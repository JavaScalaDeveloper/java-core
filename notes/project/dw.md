## 一、ClickHouse 集群（DLB 流量等近实时分析）

### 1.1 配置概览

| 项 | 说明 |
|----|------|
| 版本 | **ClickHouse 26.7.x 稳定版**（当前最新 stable，如 `26.7.5`；生产以公司镜像锁定小版本为准） |
| 部署形态 | **集群模式**（多分片 + 副本，对外 Distributed / 直写本地表） |
| 规格 | 共 **512 CU**；**1 CU = 1C4G** → 合计约 **512 核 CPU / 2TB 内存** |
| 数据窗口 | 主要保留 **近 7 天** 热数据（TTL / 分区按天滚动清理） |
| 核心负载 | **DLB** 流量明细及周边分析数据 |

### 1.2 存储的业务数据

| 数据 | 量级（口述） | 用途 |
|------|--------------|------|
| DLB **B 端**流量 | **每小时几十亿** 级事件/日志 | B 端链路分析、排障、报表 |
| DLB **C 端**流量 | **每小时几十亿** 级事件/日志 | C 端体验/转化相关分析 |
| 其他数据 | 按业务接入 | 维表、汇总、旁路指标等 |

特点：**超高写入吞吐 + 短窗口热存 + 分析型查询**，适合列存 MergeTree 族；不适合当 OLTP 主库。

### 1.3 架构要点（可展开讲）

```text
采集 / 网关 / 日志管道
        ↓
   Kafka / 消息缓冲（削峰）
        ↓
  Flink / 写入服务（批量 INSERT）
        ↓
 ClickHouse 集群（512 CU）
   ├─ 分片：打散 B/C 端海量明细
   ├─ 副本：读写可用、机器故障兜底
   └─ 按天分区 + TTL ≈ 保留近 7 天
        ↓
  即席查询 / 报表 / 排障平台
```

**选型与设计理由（面试话术）：**

1. **为何 ClickHouse**：列存 + 向量化，适合宽表扫、过滤聚合；写入可批量 append，扛每小时百亿级事件量级。  
2. **为何集群 + 512 CU**：单机盘与 CPU 扛不住「B+C 双端每小时各几十亿」；水平分片并行写/扫，副本保可用。  
3. **为何只留近 7 天**：明细极热、体量极大，全量长期存成本不可接受；7 天覆盖排障与近实时运营，更久数据可入湖/冷存。  
4. **CU 换算**：512 × (1C4G) ≈ **512C + 2048G**，便于和面试官对齐资源规模。

### 1.4 工程注意点（加分）

- **批量写**：禁止逐行 INSERT；Kafka → 攒批 / Flink / Buffer，控制 part 数量。  
- **分区**：`PARTITION BY toYYYYMMDD(...)`，TTL 删过期分区。  
- **ORDER BY**：按高频过滤字段（如时间、业务 ID）设计，避免全分片盲扫。  
- **分片键**：避免热点（如纯时间单调）；按业务 ID hash 打散。  
- **查询**：限制时间窗、强制带分区条件；大查询走异步/预聚合表。  
- **副本与 Keeper**：ReplicatedMergeTree + ClickHouse Keeper，关注复制延迟与磁盘。

### 1.5 口述 30 秒

「在得物负责/参与 DLB 流量分析侧的 ClickHouse：用当前 **26.7 稳定版集群**，资源约 **512 CU（1C4G）**，存 **近 7 天** 数据。其中 DLB **B 端、C 端流量都是每小时几十亿** 量级，外加其他分析数据。整体是 Kafka 削峰 + 批量写入 + 按天分区 TTL，用列存扛超高写入和短窗口明细分析。」

## 二、数据安全分类分级扫描

### 2.1 业务与规模

| 资产类型 | 量级（单日待扫口径） | 说明 |
|----------|----------------------|------|
| 总体 | **千万级** / 日 | 需在可接受窗口内扫完或扫一轮 |
| **API** | **百万级** | 接口、字段、报文样例等 |
| **数据库** | **百万级** | MySQL、自建 Hive、ClickHouse、TiDB、ES 等库表/字段/样例 |
| **Topic** | **十万级** | Kafka/Pulsar 等主题与 schema/样例 |

目标：对资产做 **敏感数据识别 + 分类分级**（正则规则 + AI 模型辅助），支撑合规与治理。

### 2.2 架构：Manager + Pulsar + Worker

```text
资产元数据（API / DB / Topic …）
        ↓
   Manager（分页拉待扫资产）
        ↓ 投递扫描任务
     Pulsar Topic（削峰、解耦、可堆积）
        ↓ Shared 订阅
   Worker × 60 Pod
        ├─ 消费任务
        ├─ 线程池：拉样例 / 正则匹配 / AI 分类分级
        └─ 写回结果（分级标签、命中规则等）
```

| 角色 | 职责 |
|------|------|
| **Manager** | 分页查待扫资产、组装任务、控节奏投递 Pulsar；可按类型/优先级分 Topic |
| **Pulsar** | 缓冲千万级任务；Worker 扩缩容不丢积压能力 |
| **Worker** | 60 Pod 消费；Pod 内多线程做 **正则 + AI** 检测 |

**为何这样拆：** 扫描耗时不均（有的只要正则，有的要打 AI），用消息队列把「调度」和「重活」分开，Worker 水平扩到 60 扛吞吐。

### 2.3 吞吐粗算（定线程池前先有数）

设单日目标 **N = 1e7**（一千万，可按真实监控替换）：

| 窗口 | 集群平均 QPS | 单 Pod 平均（÷60） |
|------|--------------|-------------------|
| 摊满 24h | ≈ 116 任务/s | ≈ **2** 任务/s |
| 要求 8h 扫完 | ≈ 347 任务/s | ≈ **6** 任务/s |
| 要求 4h 扫完 | ≈ 694 任务/s | ≈ **12** 任务/s |

单任务耗时往往被 **AI 推理/HTTP** 主导（正则通常毫秒～几十毫秒）。

```text
单 Pod 需要的并发 ≈ 单 Pod 目标 QPS × 单任务平均耗时(秒)
例：6 任务/s × 0.5s AI ≈ 需约 3 个并行「AI 槽」；留余量与长尾 → 设计 8～16 更稳
```

**结论：** 线程池不要按「CPU×2 随便开 200」；先按 **目标完成窗口 × AI 平均延迟** 算并发，再和 **CPU 核数、下游 AI 限流** 取最小。

### 2.4 Worker 线程池怎么设？（核心）

扫描链路通常是 **混合负载**：

| 阶段 | 类型 | 线程倾向 |
|------|------|----------|
| 拉元数据/样例（DB/ES/Hive） | **IO** | 可多于核数 |
| 正则 / 规则引擎 | **CPU** | ≈ 核数 |
| AI 分类分级（HTTP/gRPC） | **IO + 下游限流** | 多于核数，但必须 **有上限** |

#### 推荐形态：两个池（或一池 + 信号量）

```text
Pulsar 消费线程（少量）
    → 提交到 ioOrCpuExecutor（拉样例 + 正则）
        → 命中/需 AI 时 → aiExecutor（或 Semaphore 限流）
            → 写回结果
```

| 池 | 建议（以常见 **4C8G / 8C16G** Pod 为例） | 说明 |
|----|------------------------------------------|------|
| **消费侧** | Pulsar client 并发消费 **1～4** / Pod（Shared 下 60 Pod 已够散） | 消费太猛只会把本地队列打爆；长耗时任务用业务线程池消化 |
| **正则/本地检测池** | `core = CPU`，`max = CPU` 或 `CPU+2`；**有界队列** 200～2000 | CPU 型，多了无增益、徒增切换 |
| **AI 调用池** | `core = 8～16`（4C）或 `16～32`（8C）；`max` 同级或略高；队列 500～5000 | 按「QPS×延迟」算；**不得超过 AI 网关单 Pod / 集群配额** |
| **拒绝策略** | `CallerRuns` 或自定义「延迟 ack / 负反馈降速」 | 勿静默 Discard；要能反压到 Pulsar 消费 |

#### 经验公式（可写进述职）

```text
aiMaxThreads ≈ min(
  ceil(podTargetQps × aiP99LatencySec × 1.5),  // 业务并发需求
  aiServiceQuotaPerPod,                         // 下游限流
  (CPU cores × 4)                               // 本机连接/FD/堆经验上限
)

regexThreads ≈ CPU cores
```

**4C Pod 起步参考（可压测微调）：**

```text
regexPool:   core=4,  max=4,  queue=1000,  CallerRuns
aiPool:      core=12, max=16, queue=2000, CallerRuns
pulsar:      receiverQueueSize=100～500；ack 在任务真正结束后再提交
```

**8C Pod 可同比放大 AI 池到 24～32**，仍受 AI 集群总 QPS 约束：  
`60 × aiMaxPerPod` 不得超过模型服务容量，否则全面超时重试雪崩。

#### 务必和 Pulsar 消费联动

| 点 | 建议 |
|----|------|
| **ack 时机** | 检测+写回成功后再 ack；避免「早 ack、晚失败」丢语义（至少一次下靠幂等） |
| **消费速率** | `receiverQueueSize`、客户端暂停消费（线程池队列高水位时 stop/resume） |
| **失败重试** | 业务重试有限次 + 死信；毒消息（坏样例）隔离 |
| **分区/Key** | 同资产 ID 进同 key，便于幂等与顺序（若需要） |

### 2.5 为何不要「一个超大线程池」

| 做法 | 问题 |
|------|------|
| 单池 200 线程全开 | 正则抢 CPU，AI 连接打满，延迟抖动，Pod OOM |
| 无线程上限 + 无界队列 | 堆积堆内存，Full GC，Pulsar 积压假象 |
| 忽略 AI 限流 | 60 Pod × 高并发 = 下游 429/超时，扫描成功率崩 |

**正确姿势：** **CPU 池小而稳 + AI 池按配额封顶 + 队列有界 + 反压消费**。

### 2.6 压测与调参步骤（落地）

1. 固定 Pod 规格与 60 副本，先只开正则，量吞吐上限。  
2. 再开 AI，从 `aiMax=4` 阶梯加到 8/12/16，看 **成功率、P99、下游 QPS、Pod CPU/内存**。  
3. 画曲线：线程↑ 但成功率↓ 或 P99↑ → 已超下游或本机瓶颈，回退一档。  
4. 按资产类型拆 Topic/优先级（API vs 大表样例），避免大任务饿死小任务。  
5. 监控：Pulsar backlog、线程池 active/queue、AI 错误率、单日完成率。

### 2.7 口述 30～60 秒

「数据安全分类分级要 **单日扫千万级资产**：API、库表（MySQL/Hive/CH/TiDB/ES）、Topic 合计这个量级。我们用 **Manager 分页投 Pulsar，60 个 Worker Pod 消费**；Pod 里多线程做正则和 AI。线程池上 **正则按核数**，**AI 按『目标 QPS×延迟』和模型限流取 min**，有界队列 + 反压消费，避免 60 副本把 AI 打挂。最终以压测收敛具体 core/max，而不是拍脑袋开几百线程。」

## 三、数据安全 / 隐私合规业务知识（等保 2.0 等）

> 工程侧做的是 **分类分级扫描、标签、治理落地**；面试要能把 **法规要求 → 业务动作 → 技术能力** 串起来。  
> 口述口径以公司法务/安全部正式解读为准，下列为行业通用要点。

### 3.1 国内「三法」与岗位关系

| 法规 | 核心关切 | 和数据安全岗的关系 |
|------|----------|-------------------|
| **《网络安全法》** | 网络运行安全、关键信息基础设施、等保 | 系统要定级备案、满足等保技术/管理要求 |
| **《数据安全法》** | 数据分类分级、重要数据、出境、风险监测 | **分类分级**、重要数据目录、全生命周期安全 |
| **《个人信息保护法》（个保法）** | 个人信息处理合法性、最小必要、知情同意、敏感个人信息 | 识别 PII/敏感字段、脱敏、权限、留存、对外提供 |

**一句话：** 等保偏 **系统与网络防护**；数安法偏 **数据本身**；个保法偏 **人的信息**。得物分类分级扫描同时服务 **数安法 + 个保法** 落地。

### 3.2 等保 2.0 是什么？

**等保** = 网络安全等级保护；**2.0** 指以 GB/T 22239-2019 等为代表的新一代标准（相对 1.0 强化了云计算、大数据、物联网、移动互联、工控等扩展要求，以及主动防御、态势感知等）。

#### 定级（常见互联网业务）

| 级别 | 大致含义 | 互联网公司常见 |
|------|----------|----------------|
| **一级** | 损害个体、公民合法权益 | 少见独立定级 |
| **二级** | 一般损害社会秩序/公共利益 | 普通业务系统常见 |
| **三级** | 严重损害社会秩序/公共利益，或一般损害国家安全 | **核心交易、支付、用户中心、大数据平台** 等高敏系统常定三级 |
| **四级/五级** | 特别严重 / 国家安全 | 一般非电商主营 |

**口述：** 定级看 **业务重要性 + 数据敏感程度 + 受损影响面**；定级后 **备案 → 建设整改 → 测评 → 监督检查**。

#### 等保 2.0 技术要求骨架（面试画表）

```text
安全物理环境 → 安全通信网络 → 安全区域边界 → 安全计算环境
                              ↑
                         安全管理中心（集中管控）
```

| 类 | 典型要求（技术向口述） |
|----|------------------------|
| **身份鉴别** | 实名/实人、复杂度、多因素（三级常见） |
| **访问控制** | 最小权限、分权、重要操作审批 |
| **安全审计** | 登录、操作、管理行为可追溯、防篡改 |
| **入侵防范 / 恶意代码** | WAF、主机防护、病毒库 |
| **数据完整性 / 保密性** | 传输加密（TLS）、存储加密或关键字段加密 |
| **备份恢复** | 重要数据备份、恢复演练 |
| **剩余信息保护** | 介质擦除、逻辑删除后不可恢复策略 |

**管理要求：** 安全管理制度、人员、建设、运维（含应急、变更、外包）。测评机构按 **技术+管理** 打分，有高风险项必须整改。

#### 等保 2.0 相对 1.0 的加分口述

- 覆盖 **云、大数据、移动、物联网、工控** 扩展要求。  
- 更强调 **主动防御、安全监测、态势感知、可信验证**。  
- 大数据场景：关注 **数据生命周期、脱敏、接口安全、多租户隔离** 等。

### 3.3 分类分级（数安法落地的核心动作）

#### 业务目标

| 目标 | 说明 |
|------|------|
| **摸清家底** | 哪些库表/API/Topic 含敏感数据 |
| **定级打标** | 按敏感程度贴标签（公开/内部/敏感/机密 等，以公司标准为准） |
| **差异化管控** | 高级别 → 更强权限、加密、审计、出境限制 |
| **支撑合规** | 重要数据识别、个保法敏感个人信息、审计举证 |

#### 常见分级思路（示例，非官方唯一标准）

| 级别（示例） | 典型数据 | 管控倾向 |
|--------------|----------|----------|
| **公开** | 已公示商品信息 | 常规访问 |
| **内部** | 一般业务日志、非敏感运营指标 | 内网 + 账号权限 |
| **敏感** | 手机号、地址、订单明细、设备标识 | 脱敏展示、下载审批、审计 |
| **高敏感 / 机密** | 身份证、生物特征、完整银行卡、精确行踪 | 强加密、极少数授权、严格留存与出境 |

**敏感个人信息（个保法常考）：** 生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹等，以及不满十四周岁未成年人信息等——处理要求更高（单独同意等，以法务口径为准）。

#### 和「扫描工程」的对应

```text
法规要求「分类分级」
        ↓
资产盘点（API / DB / Topic）
        ↓
规则（正则）+ AI 识别字段语义
        ↓
输出：敏感类型标签 + 建议级别
        ↓
下游：权限系统、脱敏、加密、数据地图、审计、出境评估
```

扫描本身 **不等于合规完成**，只是 **发现与打标**；真正合规靠 **管控闭环**。

### 3.4 隐私合规（个保法）业务要点

| 原则 | 业务含义 | 技术落点（可举例） |
|------|----------|-------------------|
| **合法正当必要** | 有目的、有依据、不过度采集 | 字段最小化、接口裁剪 |
| **知情同意** | 告知处理目的、方式、范围 | 隐私政策、授权开关 |
| **最小必要** | 能不采就不采、能脱敏则脱敏 | 分类分级后的字段治理 |
| **公开透明** | 规则清晰可查 | 隐私政策、权限说明 |
| **质量 / 安全** | 准确、防泄露篡改丢失 | 加密、脱敏、审计、防泄漏（DLP） |
| **主体权利** | 查阅、复制、更正、删除、注销 | 用户中心能力 + 后端任务 |

**常见业务场景：**

- **日志/大数据平台**：样例、明细是否含手机号明文 → 扫描发现 → 脱敏或降级存储。  
- **测试环境**：禁止直接用生产明文；需脱敏子集。  
- **对外提供 / 出境**：合同 + 评估；重要数据/个人信息出境走评估或标准合同等路径（法务主导）。  
- **第三方 SDK / 供应商**：最小授权、审计、协议约束。

```text
└──────────────────────────────────────────┘
```

| **等保** | 大数据/分析系统按定级做访问控制、审计、通信加密等 |

### 3.6 等保测评常见「大数据/平台」考点（口述）

1. **账号与权限**：生产库/CH/Hive 是否共用超管、是否最小权限。  
2. **传输与存储**：公网/跨机房是否 TLS；敏感字段是否加密或脱敏。  
3. **审计**：谁查了哪张含手机号的表、导出是否留痕。  
4. **漏洞与补丁**：组件版本、高危 CVE 治理。  
5. **备份与恢复**：核心配置与重要数据备份策略。  
6. **日志自身**：审计日志防删改、留存周期。  

分类分级结果可直接支撑：**哪些资产要进「重点审计名单」、哪些禁止明文出库**。

### 3.7 和 ClickHouse / 扫描项目的交叉叙述

| 项目 | 合规叙事 |
|------|----------|
| **CH 存 DLB 近 7 天流量** | 生命周期（最短必要留存）+ 访问控制 + 查询审计；明细是否含 PII 需分级结果约束 |
| **分类分级扫描** | 数安法分类分级 + 个保法敏感识别的 **自动化发现能力**；吞吐与准确率是工程指标，合规闭环是业务指标 |

### 3.8 面试追问速答

| 追问 | 要点 |
|------|------|
| 等保几级？ | 按系统定级，核心用户/交易/大数据平台常见 **三级** 口径（以公司备案为准） |
| 等保和 ISO27001？ | 等保是中国监管测评；ISO 是管理体系认证；可并行，要求不完全等同 |
| 分类和分级区别？ | **分类**按业务/敏感类型（如手机号、身份证）；**分级**按影响程度定管控强度 |
| 扫描准确率？ | 正则高召回易误报；AI 补语义；人工抽检 + 规则迭代；关键类型可白名单/确认流 |
| 发现后谁整改？ | 安全给政策与工单；业务/数据 Owner 改表、脱敏、下线字段；平台提供能力 |

### 3.9 口述 60 秒（安全业务向）

「国内合规主要看网安法、数安法、个保法。等保 2.0 是系统侧等级保护，定级备案后按技术和管理要求整改测评，三级常见于核心系统。数安法要求数据分类分级，个保法管个人信息尤其是敏感个人信息。我们在得物做的分类分级扫描，就是对 API、库表、Topic 等资产做敏感识别和打标，用正则加 AI 扛千万级日扫，输出标签给权限、脱敏、审计等下游，形成发现到管控的闭环，而不是只扫不治。」
