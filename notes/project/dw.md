## 一、ClickHouse 集群（DLB 流量等近实时分析）

### 1.1 配置概览

| 项 | 说明 |
|----|------|
| 版本 | **ClickHouse 26.7.x 稳定版**（当前最新 stable，如 `26.7.5`；生产以公司镜像锁定小版本为准） |
| 部署形态 | **集群模式**（多分片 + 副本，对外 Distributed / 直写本地表） |
| 规格 | 共 **512 CU**；**1 CU = 1C4G** → 合计约 **512 核 CPU / 2TB 内存** |
| 数据窗口 | 主要保留 **近 7 天** 热数据（TTL / 分区按天滚动清理） |
| 核心负载 | **DLB** 流量明细及周边分析数据 |

### 1.2 存储的业务数据

| 数据 | 量级（口述） | 用途 |
|------|--------------|------|
| DLB **B 端**流量 | **每小时几十亿** 级事件/日志 | B 端链路分析、排障、报表 |
| DLB **C 端**流量 | **每小时几十亿** 级事件/日志 | C 端体验/转化相关分析 |
| 其他数据 | 按业务接入 | 维表、汇总、旁路指标等 |

特点：**超高写入吞吐 + 短窗口热存 + 分析型查询**，适合列存 MergeTree 族；不适合当 OLTP 主库。

### 1.3 架构要点（可展开讲）

```text
采集 / 网关 / 日志管道
        ↓
   Kafka / 消息缓冲（削峰）
        ↓
  Flink / 写入服务（批量 INSERT）
        ↓
 ClickHouse 集群（512 CU）
   ├─ 分片：打散 B/C 端海量明细
   ├─ 副本：读写可用、机器故障兜底
   └─ 按天分区 + TTL ≈ 保留近 7 天
        ↓
  即席查询 / 报表 / 排障平台
```

**选型与设计理由（面试话术）：**

1. **为何 ClickHouse**：列存 + 向量化，适合宽表扫、过滤聚合；写入可批量 append，扛每小时百亿级事件量级。  
2. **为何集群 + 512 CU**：单机盘与 CPU 扛不住「B+C 双端每小时各几十亿」；水平分片并行写/扫，副本保可用。  
3. **为何只留近 7 天**：明细极热、体量极大，全量长期存成本不可接受；7 天覆盖排障与近实时运营，更久数据可入湖/冷存。  
4. **CU 换算**：512 × (1C4G) ≈ **512C + 2048G**，便于和面试官对齐资源规模。

### 1.4 工程注意点（加分）

- **批量写**：禁止逐行 INSERT；Kafka → 攒批 / Flink / Buffer，控制 part 数量。  
- **分区**：`PARTITION BY toYYYYMMDD(...)`，TTL 删过期分区。  
- **ORDER BY**：按高频过滤字段（如时间、业务 ID）设计，避免全分片盲扫。  
- **分片键**：避免热点（如纯时间单调）；按业务 ID hash 打散。  
- **查询**：限制时间窗、强制带分区条件；大查询走异步/预聚合表。  
- **副本与 Keeper**：ReplicatedMergeTree + ClickHouse Keeper，关注复制延迟与磁盘。

### 1.5 口述 30 秒

「在得物负责/参与 DLB 流量分析侧的 ClickHouse：用当前 **26.7 稳定版集群**，资源约 **512 CU（1C4G）**，存 **近 7 天** 数据。其中 DLB **B 端、C 端流量都是每小时几十亿** 量级，外加其他分析数据。整体是 Kafka 削峰 + 批量写入 + 按天分区 TTL，用列存扛超高写入和短窗口明细分析。」
