# ZooKeeper 面试题

> 定位：分布式协调（而非业务数据库）。典型用途：配置中心、命名服务、分布式锁、选主、集群成员管理。Kafka（老）、HBase、Dubbo、Solr 等曾重度依赖。

---

## ZooKeeper 是什么？适合干什么？不适合干什么？

| 适合 | 不适合 |
|------|--------|
| 少量关键元数据协调 | 海量业务数据存储 |
| 选主、锁、配置推送 | 高吞吐写业务数据 |
| 集群成员感知（临时节点） | 大文件、复杂查询 |

Znode 建议 **数据量很小**（通常 KB 级，官方建议远小于 1MB）。写走 Leader，读可从 Follower，**强一致偏 CP**（分区时可能拒绝写以保证一致）。

---

## 数据怎么存？有哪些数据结构？

### 数据模型

层次化树，类似文件系统：

```text
/
 ├─ app
 │   ├─ config
 │   └─ locks
 └─ services
     └─ order-service
```

每个路径对应一个 **Znode**，可存小数据 + 元数据（版本、ACL、时间戳等）。

### Znode 类型

| 类型 | 特点 |
|------|------|
| **持久（Persistent）** | 客户端断开仍存在，需主动删 |
| **临时（Ephemeral）** | 会话结束自动删，适合心跳/成员列表 |
| **持久顺序（Persistent Sequential）** | 持久 + 路径后缀单调序号 |
| **临时顺序（Ephemeral Sequential）** | 临时 + 序号，**分布式锁常用** |
| **Container / TTL**（3.5+） | 容器节点、带 TTL 的节点（进阶） |

可组合：持久/临时 × 是否顺序。

### 存储与持久化

- **内存**：DataTree 存全量 Znode，读快。  
- **事务日志（Transaction Log）**：写操作先记盘上事务日志。  
- **快照（Snapshot）**：定期把内存树刷到磁盘；重启 = 加载快照 + 回放日志。  

一句话：**内存树 + 事务日志 + 快照**，不是靠 DB 表存业务行。

### 相关概念

| 概念 | 作用 |
|------|------|
| **Watcher** | 一次性监听，节点变化回调客户端 |
| **ACL** | 节点访问控制（world/auth/digest/ip） |
| **Stat / 版本号** | czxid、mzxid、version，乐观锁防并发覆盖 |
| **Session** | 客户端与集群会话；超时则临时节点删除 |

## Watcher 机制有什么坑？

1. **一次性**：触发后需重新注册，否则后续变化收不到。  
2. **不保证每次变更都通知到**（极端网络/丢事件场景要设计幂等拉全量）。  
3. **羊群效应**：很多人 Watch 同一节点 → 节点删时惊群；锁实现应 Watch **前驱节点** 而非父节点所有子节点。  
4. 通知是 **异步** 的，收到通知后应再 `getData`/`getChildren` 拉最新，不要只信通知内容。

## 读写流程？谁能写？

### 角色

| 角色 | 职责 |
|------|------|
| **Leader** | 处理写请求，发起提案，协调事务 |
| **Follower** | 参与投票；可处理读；转发写给 Leader |
| **Observer** | 只同步不投票，扩展读能力、跨机房 |

### 写（简化）

```text
Client → Follower（可选）→ 转发 Leader
  → Leader 提案（Proposal）
  → 过半 Follower ACK
  → Leader Commit → 各节点应用到内存树
  → 响应 Client
```

### 读

可从任意连上的服务器读本地内存；为强一致可读可走 **sync** 再读（先与 Leader 对齐）。

## ZAB 协议是什么？和 Paxos / Raft 关系？

**ZAB（ZooKeeper Atomic Broadcast）**：为 ZK 设计的原子广播协议，保证副本顺序一致。

两阶段常见口述：

1. **崩溃恢复 / 选主**：选出 Leader，同步落后节点，统一 epoch。  
2. **消息广播**：Leader 广播写提案，过半确认后提交。

对比：

| | ZAB | Raft | Paxos |
|--|-----|------|-------|
| 定位 | ZK 专用原子广播 | 通用共识（etcd 等） | 通用共识理论 |
| 选主 | 有 Leader | 强依赖 Leader | 多提案者更绕 |
| 工程 | ZK 内置 | etcd、不少中间件 | 多变体 |

面试：**ZK 一致性靠 ZAB，不是简单主从异步复制。**

## 为什么说 ZooKeeper 是 CP？

CAP 中 ZK 优先 **Consistency + Partition tolerance**：

- 写需 **过半** 节点确认（法定人数）。  
- 集群存活节点 ≤ 半数时，**可能无法选主/无法写**，服务不可用，但不返回过期不一致写入。  
- 读默认可能略滞后；要线性一致可读需配合 sync。

对比：老 Eureka 偏 AP；etcd 也偏 CP；Nacos 可切换。

## Leader 选举怎么做？（口述）

常见场景：集群启动、Leader 宕机。

简化逻辑（结合 zxid、myid）：

1. 节点进入 Looking，互相投票。  
2. 比较：**优先更大 epoch/zxid**（数据更新），再比较 **myid**。  
3. 得票过半 → 成为 Leader，进入 Leading；其余 Follower。  
4. Leader 与 Follower **数据同步** 后再对外服务。

集群规模建议 **奇数**（3、5、7）：容忍 `(n-1)/2` 台宕机；再多延迟/投票成本上升。

---

## Session、临时节点与「假死」

- 客户端与 ZK 维持 **Session**，靠心跳/请求续期。  
- `sessionTimeout` 内无有效通信 → 会话过期 → **临时节点删除** → Watch 触发。  
- 用途：服务注册（Dubbo）、锁持有者宕机自动释放。  
- 注意：GC/网络抖动可能导致误过期 → 临时节点没了 → 业务要能重新注册。

## ZooKeeper 怎样实现分布式锁？

### 标准做法（临时顺序节点 + 只 Watch 前驱）

```text
1. 在 /locks 下创建临时顺序节点：/locks/lock-000000003
2. getChildren，判断自己是否序号最小
   - 是 → 持有锁
   - 否 → Watch 序号刚好比自己小的前一个节点
3. 收到前驱删除通知 → 再检查是否最小（防误唤醒）
4. 业务结束 delete 自己的节点；进程挂了会话结束自动删
```

### 为什么这样设计？

| 点 | 原因 |
|----|------|
| 临时 | 宕机自动释放，防死锁 |
| 顺序 | 公平排队，FIFO |
| Watch 前驱 | 避免所有人 Watch 父节点造成 **羊群效应** |

### 可重入 / 读写锁（了解）

- 可重入：线程本地计数 + 同一客户端标识。  
- 读写锁：不同类型顺序节点（如 `/locks/R-`、`/locks/W-`）按规则判断能否共享。

### 和 Redis 锁对比

| | ZK 锁 | Redis 锁 |
|--|-------|----------|
| 一致性 | 强，易正确 | 实现易错（过期、误删） |
| 性能 | 较弱（写走法定人数） | 高 |
| 场景 | 强正确、低频临界区 | 高并发、可接受复杂边界 |
| 运维 | 依赖 ZK 集群 | 依赖 Redis 高可用 |

Curator 的 `InterProcessMutex` 封装了上述模式，生产优先用成熟库。

## 其他经典用法

### 1. 选主（Leader Election）

多个候选在同一路径下建临时顺序节点，**最小序号当 Leader**；挂了自动重选。  
用途：集群内单点调度、主备切换。

### 2. 配置中心

配置放持久 Znode；客户端 Watch；变更推送。  
现代更多用 Nacos/Apollo；ZK 偏「轻量配置 + 协调」。

### 3. 服务注册发现

服务实例写 **临时节点**；下线自动消失；消费者 Watch 子节点列表。  
Dubbo 早期 registry；现多 Nacos/Kubernetes。

### 4. 分布式队列 / 屏障

顺序节点模拟队列；Barrier：到齐再继续（了解即可）。

## 常见面试追问

**1. ZK 能当消息队列吗？**  
不适合。吞吐低、节点不宜大、无消费组语义；用 Kafka/RocketMQ。

**2. 脑裂怎么防？**  
写需过半；少数派无法选主成 Leader，避免双主写入。

**3. zxid 是什么？**  
64 位事务 ID（epoch + 计数），标识提案顺序，选举和同步用。

**4. 客户端 API 常用哪些？**  
`create` / `delete` / `exists` / `getData` / `setData` / `getChildren` + Watch；或 Curator 高级配方。

**5. 和 etcd、Nacos 怎么选？**  

| | ZK | etcd | Nacos |
|--|-----|------|-------|
| 协议 | ZAB | Raft | 自研 + CP/AP 可选 |
| 强项 | 经典协调、锁、选主 | K8s、云原生 | 注册+配置一体（国内微服务） |
| 接口 | Znode 树 | KV | HTTP/服务发现语义 |

**6. 观察者 Observer 什么时候用？**  
扩展读、跨机房同步又不增加投票人数（不拖累写法定人数）。

**7. 数据不一致怎么办？**  
Follower 从 Leader 同步；崩溃恢复阶段对齐；客户端重要读可 `sync`。

## 面试速记

| 主题 | 一句话 |
|------|--------|
| 定位 | 分布式协调，非业务库 |
| 存储 | 内存 DataTree + 事务日志 + 快照 |
| Znode | 持久/临时/顺序；锁用临时顺序 |
| Watch | 一次性；防羊群要 Watch 前驱 |
| 协议 | ZAB；写过半提交；偏 CP |
| 角色 | Leader 写；Follower 投票；Observer 只同步 |
| 锁 | 临时顺序节点 + 最小获锁 + Watch 前驱 |
| 选主 | 序号最小或选举投票过半 |
| 对比 | 正确性强、性能一般；高频锁可看 Redis |

**30 秒收口：**  
「ZooKeeper 用树形 Znode 做协调，写走 Leader+ZAB 过半提交，偏 CP。分布式锁用临时顺序节点，谁最小谁持锁，只监听前一个节点避免惊群。适合选主、配置、成员管理，不适合存大数据或当 MQ。」
