# 分布式事务面试题

> 核心结论：**尽量不用强分布式事务**；能最终一致就消息 + 幂等 + 补偿。必须跨库原子时再选 Seata / TCC / XA。  
> MQ「事务」≠ 数据库事务：要分清 **RocketMQ 半消息**、**Kafka/Pulsar 消息系统内事务**、**Seata 跨服务事务**。

---

## CAP 与分布式事务怎么答？

### CAP 一句话

分区（P）几乎必须接受时，只能在 **C（强一致）** 和 **A（可用性）** 之间权衡。

| 倾向 | 典型 | 事务含义 |
|------|------|----------|
| **CP** | ZK、etcd、多数共识写、2PC/Seata AT | 宁可短暂不可用，也不返回错提交 |
| **AP** | 最终一致、异步复制、柔性事务 | 先可用，靠补偿/对账追齐 |

分布式事务讨论的「一致性」多为 **多资源提交结果一致**（全成功或全失败/可补偿），不是 CAP 里每一次读都立刻看到最新写的狭义 C。

### 选型口诀

- 下单扣库存、资金：偏 **强一致或可补偿的严格流程**（TCC / Seata / 对账）。  
- 发积分、发通知：偏 **最终一致**（本地消息表 / 事务消息）。  
- 流计算链路：偏 **Kafka/Pulsar 内 EOS**，库表另做幂等。

## 常见方案对比（先画这张表）

| 方案 | 思想 | 优点 | 缺点 | 典型场景 |
|------|------|------|------|----------|
| **2PC / XA** | 协调者两阶段提交 | 对业务侵入小 | 阻塞、性能差、协调者单点 | 传统单体拆库 |
| **Seata AT** | 改 SQL + undo_log，自动补偿 | 侵入小 | 依赖代理/改造、长事务、脏读窗口要懂 | Spring Cloud 多库 |
| **TCC** | Try / Confirm / Cancel | 性能可控、明确 | 业务侵入大，要写空回滚、防悬挂 | 资金、强一致业务 |
| **Saga** | 正向 + 补偿链 | 适合长流程 | 补偿难写全 | 订单履约长链路 |
| **本地消息表 / Outbox** | 本地事务写业务+消息 | 简单可靠 | 最终一致 | 最常用工程方案 |
| **RocketMQ 事务消息** | 半消息 + 本地事务 + 回查 | 解耦发消息与本地事务 | 非跨多 DB 原子 | 下单后通知下游 |
| **Kafka/Pulsar 事务** | 消息系统内原子写/Ack | 流处理 EOS | **不管 MySQL** | 消费-转换-再生产 |

## 2PC / XA 实现原理（强一致基线）

### 角色

| 角色 | 职责 |
|------|------|
| **协调者（TC）** | 发起提交/回滚，维护全局事务状态 |
| **参与者（RM）** | 各数据库/资源管理器，执行本地分支 |

### 两阶段流程

```text
阶段一 Prepare（投票）
  TC → 所有 RM：prepare
  RM：执行 SQL 但不真正提交，写 undo/redo，返回 YES/NO
  任一 NO → 全局回滚

阶段二 Commit / Rollback（决议）
  全部 YES → TC 发 commit → 各 RM 提交
  有 NO   → TC 发 rollback → 各 RM 回滚
```

### XA 与 2PC 关系

- **2PC** 是协议思想；**XA** 是 DB/驱动层的标准接口（`XAResource`）。  
- Seata **XA 模式**：各 RM 走数据库 XA 两阶段，由 Seata TC 协调。  
- **特点**：业务几乎无侵入；**阻塞**（Prepare 后锁资源直到 Commit/Rollback）；协调者单点；长事务性能差。

### 三大经典问题

| 问题 | 含义 |
|------|------|
| **同步阻塞** | Prepare 后资源被锁，其他事务等待 |
| **单点故障** | TC 宕机，参与者一直阻塞 |
| **数据不一致（脑裂）** | Commit 时部分 RM 收到、部分未收到 → 需人工/补偿 |

**面试收口**：2PC 理论正确、工程上因阻塞和协调者问题，互联网高并发场景少用；Seata AT 用 undo 异步二阶段缓解，但仍要控制事务时长。

## Saga 实现原理

**思想**：长事务拆成多个**本地事务**串联；某步失败则按逆序执行**补偿事务**（不是回滚日志，是业务反向操作）。

### 两种编排

| 模式 | 谁协调 | 特点 |
|------|--------|------|
| **编排（Orchestration）** | 中心协调器发命令 | 状态清晰，Seata Saga 状态机 |
| **协同（Choreography）** | 各服务监听事件自行推进 | 去中心，链路难追踪 |

```text
正向：T1 下单 → T2 扣库存 → T3 支付
失败在 T3：C2 还库存 → C1 关订单
```

### 与 TCC / 2PC 区别

- **无全局锁、无 Prepare 阻塞**；每步本地事务立即提交。  
- **补偿是业务语义**（取消订单），不是 DB 自动 undo。  
- **隔离性弱**：补偿完成前，其他事务可能读到中间态 → 需语义隔离或防重设计。

## 本地消息表 / Outbox（优先掌握）

```text
同一本地事务：
  1. 写业务表（订单）
  2. 写 outbox 表（待发消息）
提交 DB
  → 异步轮询/CDC 发 MQ
  → 下游幂等消费
```

保证：**不会出现「库写成功但消息彻底丢了」**（最多重复发 → 下游幂等）。  
这是和 RocketMQ 事务消息同一类问题的不同实现。

### 实现原理（细）

```text
┌─────────────────────────────────────────────────┐
│  本地 DB 事务（原子）                              │
│    INSERT order ...                              │
│    INSERT outbox(status=PENDING, payload=...)   │
│  COMMIT                                          │
└─────────────────────────────────────────────────┘
         │
         ▼
  投递器（三选一或组合）
  ① 定时轮询 PENDING → 发 MQ → 标 SENT
  ② CDC（Debezium/Canal）监听 binlog → 发 MQ
  ③ 事务提交后异步线程发（仍建议 outbox 表做状态）
         │
         ▼
  下游幂等消费（业务唯一键 / 去重表）
```

| 环节 | 要点 |
|------|------|
| **原子性** | 业务与 outbox **同一本地事务** |
| **至少一次投递** | 发成功前不删记录；失败重试 |
| **重复消息** | 下游 **幂等**（唯一约束、Redis set、状态机） |
| **顺序** | 同聚合根可同 key 保序；全局顺序通常不要求 |

与 RocketMQ 半消息对比：Outbox **不绑特定 MQ**；RMQ 半消息省一张表但耦合 Broker 事务 API。

## RocketMQ 事务消息（半消息）

解决：**本地 DB 事务** 与 **「消息一定发出去」** 的最终一致。

### 实现原理（细）

```text
Producer                          Broker                    本地事务
   │                                 │                         │
   │── sendMessageInTransaction ────►│ 存 Half Message          │
   │    (half, 对 Consumer 不可见)    │  (TopicQueue)            │
   │                                 │                         │
   │◄── executeLocalTransaction ─────┼────────────────────────►│ 写订单等
   │     返回 COMMIT / ROLLBACK       │                         │
   │                                 │                         │
   │── COMMIT ──────────────────────►│ 半消息 → 正常消息，可消费  │
   │  或 ROLLBACK                    │ 或丢弃                   │
   │                                 │                         │
   │◄── checkLocalTransaction ───────┼── 若长时间无结果，Broker 回查
   │     (回查本地事务状态)            │                         │
```

| 步骤 | 原理 |
|------|------|
| **Half Message** | 先落盘到 Broker，**不进入消费队列可见位点** |
| **本地事务** | Producer 回调里执行业务 SQL，与发消息解耦在同一流程 |
| **Commit/Rollback** | 决定半消息是否对消费者可见 |
| **回查** | 网络闪断、Producer 宕机时，Broker 主动问「这笔本地事务到底成功没」 |

- 管的是 **发消息 ↔ 本地事务**，不是两个微服务 DB 的 2PC。  
- 下游仍要 **幂等**。  
- 对比 Kafka：RMQ 更像「业务事务消息」；Kafka 事务更像「Topic 间原子写」。

## Seata 怎么实现？原理？

### 架构角色

```text
TM（@GlobalTransactional）  开启/提交/回滚全局事务
        │
        ▼
TC（Seata Server）          维护全局 XID、分支状态、驱动二阶段
        │
   ┌────┴────┐
   RM-A      RM-B            各服务内 ResourceManager，注册分支、上报状态
```

- 调用链透传 **XID**（HTTP/Feign 头、Dubbo attachment）。  
- 每个 RM 一阶段向 TC **注册分支**，二阶段听 TC 指令 commit/rollback。

### 用法（口述）

`@GlobalTransactional` 包住跨服务调用；每个服务本地 `@Transactional`；TC（Seata Server）协调全局状态。

### 模式

| 模式 | 原理 | 侵入 |
|------|------|------|
| **AT** | 解析 SQL，记 undo_log；一阶段改数据，二阶段提交删 undo / 回滚用 undo | 小 |
| **TCC** | 业务实现 try/confirm/cancel | 大 |
| **Saga** | 状态机 + 补偿 | 中 |
| **XA** | 数据库 XA | 小但慢 |

### AT 两阶段（原理深挖）

**一阶段（分支提交）**

1. 解析 SQL，查 **前镜像**（before image）。  
2. 执行业务 UPDATE/INSERT/DELETE。  
3. 查 **后镜像**（after image），生成 **undo_log**（反向 SQL）写入同一库。  
4. **本地事务提交** → 业务数据已落库（这点常被误解为「未提交」）。  
5. 向 TC 注册分支，申请/检查 **全局锁**（防脏写：别的事务改同一行需等全局事务结束）。

**二阶段**

| 全局结果 | 动作 |
|----------|------|
| **Commit** | 异步删 undo_log（数据已是最终态） |
| **Rollback** | 读 undo_log 生成反向 SQL 回滚；删 undo_log |

**全局锁**：AT 一阶段后数据可见，靠全局锁避免其他未入全局事务的写与回滚冲突；**长事务、热点行**易锁等待。

**脏读防护**：AT 默认隔离级别靠全局锁 + `@GlobalLock` 等机制，面试说「一阶段已提交，靠 undo 二阶段回滚 + 全局锁」即可。

### TCC 在 Seata 中

Try/Confirm/Cancel 由业务实现；TC 协调三阶段状态；需处理空回滚、悬挂、幂等（Seata 提供防悬挂/空回滚框架支持，业务仍要正确实现资源预留）。

## TCC 怎么讲？

把一个业务拆成三步：

| 阶段 | 做什么 | 资源状态 |
|------|--------|----------|
| **Try** | 预留资源（冻结余额、锁库存） | 可用 → 冻结 |
| **Confirm** | 确认使用预留（扣减） | 冻结 → 已用 |
| **Cancel** | 释放预留（解冻） | 冻结 → 可用 |

### 实现原理

```text
Try：   UPDATE account SET frozen = frozen + 100, available = available - 100
Confirm: UPDATE account SET frozen = frozen - 100   -- 真正扣款
Cancel:  UPDATE account SET frozen = frozen - 100, available = available + 100
```

每步都是**独立本地事务**；Confirm/Cancel 由 TC 在全局决议后异步或同步触发。

### 必须处理的异常场景

| 场景 | 原因 | 处理 |
|------|------|------|
| **空回滚** | Try 未执行成功（超时），却收到 Cancel | Cancel 前查 Try 记录，无则直接成功 |
| **悬挂** | Cancel 先于迟到的 Try 执行 | Try 前查是否已 Cancel，是则拒绝 Try |
| **幂等** | 网络重试导致重复 Confirm/Cancel | 分支状态表：INIT→TRY→CONFIRM/CANCEL |

适合资金类；开发成本高，但**无长锁、性能可控**。

## Kafka 怎么实现「分布式事务」？

先澄清边界：

| Kafka 事务能保证 | 不能保证 |
|------------------|----------|
| 多个 Topic/Partition **原子写入** | 与 MySQL 同事务提交 |
| 消费 Offset 与产出消息 **同事务提交**（EOS 链路） | 跨系统 Exactly-Once 自动成立 |
| `read_committed` 读不到未提交消息 | 业务幂等可省略 |

### 1. 幂等 Producer（事务基础）

`enable.idempotence=true` → Broker 用 **PID + 分区 + sequence** 去重，防网络重试导致重复写。  
幂等 ≠ 事务：幂等只管「同分区重试不重复」；事务管「多分区要么都成功可见」。

### 2. 事务 Producer（跨分区原子写）

```text
配置 transactional.id（稳定且唯一）
initTransactions()
beginTransaction()
  send(topicA, ...)
  send(topicB, ...)
commitTransaction()   // 或 abortTransaction()
```

机制要点（口述）：

1. 向 **Transaction Coordinator**（内部 `__transaction_state`）注册事务。  
2. 写入的消息带事务状态，对 `read_committed` 消费者 **提交前不可见**。  
3. Commit：Coordinator 标记事务完成，各分区事务结束 marker，消息对已提交读可见。  
4. Abort：消息被标记丢弃，读端看不到。

### 3. 消费-转换-生产（Exactly-Once 链路）

经典模式：**读 Topic A → 处理 → 写 Topic B**，把 **消费位移** 和 **产出** 放进同一事务：

```text
beginTransaction()
  producer.send(output)
  producer.sendOffsetsToTransaction(offsets, groupMetadata)  // Offset 进事务
commitTransaction()
```

失败 abort → Offset 未提交 → 会重新消费；下游用幂等/去重兜底极端情况。

### 4. 和「业务分布式事务」怎么接？

Kafka 事务 **解决不了**「改订单表 + 发 Kafka」的原子性，工程上：

- **Outbox**：本地事务写 DB + outbox，再发 Kafka（可用 Debezium）。  
- 或 RocketMQ 半消息（若用 RMQ）。  
- 或 Seata（重）。

**面试对比：**

| | RocketMQ 事务消息 | Kafka 事务 |
|--|-------------------|------------|
| 目标 | 本地事务 ↔ 发消息 | Topic/Offset 链路原子 |
| 回查 | 有 checkLocalTransaction | 无业务回查 |
| 跨 DB | 间接（最终一致） | 不管 DB |
| 流处理 EOS | 弱 | 强（生态成熟） |

## Pulsar 怎么实现分布式事务？

Pulsar 从较新版本起支持 **Transaction API**，语义接近「消息系统内事务」，用于流处理 / 多主题原子操作。

### 能做什么？

| 能力 | 说明 |
|------|------|
| 原子发送 | 一次事务向多个 Topic 发消息，全部成功或全部对消费者不可见 |
| 原子 Ack | 消费确认与发送放在同一事务（consume-process-produce） |
| 与缓冲 | 未 Commit 前，普通订阅读不到事务内消息（类似 read_committed） |

### 流程（口述）

```text
1. 开启事务（向 Transaction Coordinator 申请 txnID）
2. 生产：newMessage().send(txn) / 批量发往多 Topic
3. 消费：acknowledge(msgId, txn)   // Ack 绑定事务
4. txn.commit() 或 txn.abort()
```

- **Commit**：消息对订阅者可见，Ack 生效，Cursor 推进。  
- **Abort**：消息丢弃/不可见，Ack 不生效，消息可再投。

### 实现要点（原理级）

1. **TC（Transaction Coordinator）**：维护事务状态（Open / Committing / …）。  
2. **TxnID**：标识一次事务；消息与 Ack 携带 txn 元数据。  
3. 与 BookKeeper 持久化配合，保证故障后事务状态可恢复。  
4. 需 Broker / 客户端开启事务相关配置（版本与开关以官方文档为准）。

### Pulsar vs Kafka vs RocketMQ

| | Pulsar 事务 | Kafka 事务 | RocketMQ 事务消息 |
|--|-------------|------------|-------------------|
| 定位 | 多 Topic 发送 + Ack 原子 | 多分区写 + Offset 原子 | 半消息 + 本地事务回查 |
| 进度模型 | Cursor + Ack | Consumer Offset | 消费进度 + ACK |
| 业务半消息回查 | 无（不像 RMQ） | 无 | **有** |
| 流 EOS | 支持 | 成熟常用 | 非主战场 |
| 和 DB | 需 Outbox/自研 | 同左 | 半消息直接绑本地事务 |

**一句话：** Pulsar/Kafka 事务是 **消息层 EOS**；RocketMQ 事务消息是 **业务本地事务与投递**；跨库还要 Outbox 或 Seata。

---

## 端到端 Exactly-Once 怎么理解？

| 层级 | 含义 |
|------|------|
| 生产幂等 | 重试不产生重复消息 |
| 消息事务 | 多输出原子可见 |
| 消费 | 至少一次下仍可能重复 → **业务幂等** |
| 跨系统 | DB + MQ 要用 Outbox / 半消息 / 分布式事务框架 |

没有「开了 Kafka 事务就一切 Exactly-Once」这种事。

---

## 方案怎么选？（决策）

```text
只要最终一致？ → 本地消息表 / Outbox / RocketMQ 半消息
只要流链路 EOS？ → Kafka / Pulsar 事务 + 幂等消费
多服务强一致短事务？ → Seata AT（评估）或 TCC（资金）
长业务流程？ → Saga / 状态机 + 补偿
能同步调通？ → 优先避免分布式事务，改成单库或异步解耦
```

## 面试速记

| 主题 | 要点 |
|------|------|
| CAP | P 必选，C/A 权衡；事务方案各偏一侧 |
| 2PC/XA | Prepare 投票 + Commit/Rollback；阻塞、协调者单点 |
| Saga | 本地事务链 + 补偿；编排/协同 |
| 优先 | Outbox / 最终一致，少上 2PC |
| RocketMQ | 半消息 + 本地事务 + 回查 |
| Seata | TM/TC/RM；AT=undo+全局锁；TCC 三阶段 |
| Kafka | transactional.id；多分区原子写；Offset 进事务做 EOS |
| Pulsar | txn 绑 send + ack；commit 后可见 |
| 共性 | 消息事务不管业务 DB；跨系统靠 Outbox/幂等 |

**30 秒收口：**  
「分布式事务优先最终一致：本地消息表或 RocketMQ 半消息。Kafka/Pulsar 事务保证的是消息系统内多主题写入和消费位点的原子性，做流处理 Exactly-Once，不能替代 Seata 跨库。跨库强一致再用 Seata AT 或 TCC，并做好幂等和补偿。」
