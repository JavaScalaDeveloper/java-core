# 消息队列选型：场景、对比与决策

选型不是「哪个更强」，而是 **场景匹配 + 团队栈 + 运维成本 + 云厂商约束**。先定业务语义，再定产品。

---

## 先问清 8 个问题

1. **主场景**：业务解耦 / 异步削峰 / 日志采集 / 流计算 / 任务调度 / MQTT IoT？  
2. **顺序**：要不要局部有序？能否接受仅分区/队列内有序？  
3. **事务**：是否必须「本地 DB + 发消息」最终一致？（半消息/Outbox）  
4. **延迟**：是否要延迟/定时消息？延迟精度要求？  
5. **吞吐与延迟**：百万级 TPS 日志流，还是万级业务消息低延迟？  
6. **消费模型**：发布订阅多消费组？还是竞争队列？要不要广播？  
7. **积压与重试**：是否要原生重试队列、死信、可回溯多久？  
8. **运维**：能否接受多组件（如 BookKeeper）？是否必须上云托管？

---

## 常见 MQ / 流平台地图

| 类型 | 代表 | 一句话定位 |
|------|------|------------|
| 业务消息中间件 | RocketMQ、RabbitMQ | 解耦、事务/延迟/重试等业务语义强 |
| 分布式日志 / 流平台 | Kafka | 高吞吐、可回溯、流生态强 |
| 云原生消息流 | Pulsar | 存算分离、多租户、订阅模型灵活 |
| 传统/经纪模型 | ActiveMQ、RabbitMQ | 协议丰富、企业集成、中等规模 |
| 轻量 / 内存向 | Redis Stream、内存队列 | 简单异步，非强持久主通道 |
| 云厂商托管 | 各云 Kafka/RMQ/Pulsar 兼容产品 | 少运维，按云生态选 |

## 按技术场景选型

### 1. 核心业务解耦（订单、支付、履约）

**诉求**：可靠投递、事务消息或最终一致、延迟关单、失败重试/死信、局部顺序（同订单号）。

**更合适**：

- **RocketMQ**：半消息事务、延迟级别、重试+DLQ、Tag 过滤，国内业务库常见首选。  
- **RabbitMQ**：路由灵活（Exchange）、TTL/DLX，中小规模业务很合适；超大吞吐与海量积压要评估。  

**谨慎**：

- 纯 Kafka：延迟/事务/DLQ 要自建，业务团队成本高。  
- 仅 Redis：持久化与堆积能力不足，不适合资金类主路径。

### 2. 异步削峰（秒杀、突发写入）

**诉求**：抗突发、可积压、消费者平滑、快速扩容。

**更合适**：

- **Kafka / RocketMQ / Pulsar** 均可；峰值极大、后续还要流计算 → 偏 **Kafka**。  
- 业务削峰且要快速重试/死信 → 偏 **RocketMQ**。  

关键：队列深度监控、消费者扩容上限（分区/队列数）、降级开关。

### 3. 日志采集、埋点、CDC、大数据入口

**诉求**：超高吞吐、顺序追加、长期保留/回溯、对接 Flink/Spark。

**首选：Kafka**（生态事实标准）。  
Pulsar 也可做事件流，但大数据栈默认集成仍是 Kafka 更省事。

### 4. 实时流计算、事件溯源、Changelog

**诉求**：可重放、分区有序、精确一次叙事（链路内）、compact 状态主题。

**首选：Kafka**（Streams / Flink + Kafka）。  
Pulsar + Flink 亦可，看团队运维与云产品。

### 5. 延迟任务 / 定时消息（超时关单、延迟通知）

**诉求**：原生延迟或定时投递。

| 产品 | 延迟能力 |
|------|----------|
| RocketMQ | 原生延迟级别（开源）/ 定时（视版本） |
| Pulsar | 延迟/定时较友好 |
| RabbitMQ | TTL + DLX 模拟延迟 |
| Kafka | 基本自建 |

强依赖延迟 → 优先 RMQ / Pulsar / Rabbit；不要硬上「裸 Kafka」除非已有平台封装。

### 6. 强顺序（证券撮合、状态机流水）

**诉求**：某业务键严格有序。

- 所有主流 MQ 都是 **分区/队列内有序**，不是全集群全局有序。  
- 做法统一：业务键路由固定分区/队列 + 单线程（或 Key 串行）消费。  
- 全局有序只能单分区/单队列 → 吞吐差，尽量拆成局部有序。

实现成本：Kafka / RocketMQ / Pulsar（Key_Shared）都能做；选团队最熟的。

### 7. 多租户、统一消息平台（中台化）

**诉求**：租户隔离、配额、灵活订阅（独占/共享/故障转移）。

**更合适：Pulsar**（Tenant/Namespace 原生）。  
Kafka 靠 ACL+规范也能做，产品化程度通常不如 Pulsar。  
RocketMQ 多租户能力看发行版与周边。

### 8. 队列语义竞争消费 + 流语义并存

**诉求**：同一套系统既要「任务队列」又要「事件流」。

- **Pulsar**：Shared / Key_Shared / 多订阅，队列味更浓。  
- **Kafka**：多消费组是发布订阅；「任务队列」要用分区独占模型表达。  
- **RocketMQ**：集群消费偏业务队列；流生态弱于 Kafka。

### 9. 物联网 / 协议多样（MQTT、STOMP）

**更合适：RabbitMQ、EMQX（MQTT）、云 IoT 套件。**  
Kafka/RMQ 常作后端总线，前端接入用专用 IoT 网关。

### 10. 简单异步、缓存级通知

Redis Stream / 列表可做；**不可**替代核心业务 MQ。适合可丢失、可重建、体量小的场景。

## 横向对比（面试/评审用）

| 维度 | Kafka | RocketMQ | Pulsar | RabbitMQ |
|------|-------|----------|--------|----------|
| 定位 | 流/日志平台 | 业务消息中心 | 云原生消息流 | 通用经纪队列 |
| 吞吐 | 极高 | 高 | 高 | 中高 |
| 顺序 | 分区内 | 队列内 | 分区/Key_Shared | 单队列有序 |
| 事务消息 | 事务Producer（链路） | 半消息+回查（业务） | 有事务能力 | 无经典半消息 |
| 延迟消息 | 弱 | 强 | 较强 | TTL/DLX 模拟 |
| 重试/DLQ | 弱（靠应用） | 强 | 强 | DLX 成熟 |
| 消费进度 | Offset | 消费位点 | 服务端 Cursor | 队列 Ack |
| 多租户 | 一般 | 一般 | 强 | 一般（VHost） |
| 存算 | Broker 存盘 | Broker 存盘 | Broker + Bookie | Broker 内存/磁盘 |
| 运维复杂度 | 中（KRaft 后降低） | 中 | 偏高 | 较低 |
| 生态 | 大数据/流最强 | 阿里系/国内业务强 | 云原生增长中 | 企业集成/协议强 |

## 组合架构（生产常见）

很多公司不是「只选一个」：

| 通道 | 常用选择 | 原因 |
|------|----------|------|
| 业务领域事件 | RocketMQ / RabbitMQ | 事务、延迟、运维心智偏业务 |
| 日志与数据管道 | Kafka | 吞吐、回溯、Flink |
| 实时数仓/指标 | Kafka → Flink → OLAP | 流批一体 |
| 统一云上多租户 | Pulsar 或云托管 | 隔离与弹性 |

原则：**业务总线与大数据总线可以分离**，用同步任务/Connect 打通，避免一个集群扛所有语义。

## 可靠性与语义：选型时统一口径

无论选谁，评审要写清：

| 项 | 说明 |
|----|------|
| 投递语义 | 多数 At-Least-Once；Exactly-Once 需额外设计 |
| 幂等 | 消费端必做（唯一键/状态机） |
| 丢失防护 | 生产确认 + 副本/法定人数 + 消费成功再提交/Ack |
| 积压预案 | 监控 Lag/Diff、扩容上限、降级、死信 |
| 顺序范围 | 写明按哪个业务键局部有序 |

## 快速决策树

```
要对接 Flink/日志海量吞吐？ ──是──► Kafka
          │否
要半消息事务 + 延迟 + DLQ 的业务中台？ ──是──► RocketMQ
          │否
要多租户 + 存算分离 + Shared/Key_Shared？ ──是──► Pulsar
          │否
中小规模、路由灵活、协议多、团队熟 AMQP？ ──是──► RabbitMQ
          │否
仅轻量异步且可丢？ ──是──► Redis Stream（非主通道）
```

## 30 秒收口（面试）

“按场景选：日志与流计算优先 Kafka；订单支付类业务解耦、事务消息和延迟消息优先 RocketMQ；云上多租户和灵活订阅评估 Pulsar；中小业务与复杂路由看 RabbitMQ。都要接受分区/队列内有序、至少一次下的幂等，以及积压监控与死信方案。大型团队经常 Kafka + RocketMQ 分通道，而不是一个 MQ 打天下。”
