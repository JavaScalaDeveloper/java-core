# RocketMQ 架构一句话

**Producer** 发消息，**NameServer** 提供路由，**Broker** 存盘与投递，**Consumer** 按消费组拉取/推送消费。Topic 下挂多个 **MessageQueue（队列）**，队列是并行与顺序的基本单位。

| 组件 | 作用 |
|------|------|
| NameServer | 轻量路由/元数据，无强状态机，多实例平行 |
| Broker | 存储与投递；主从或 DLedger 等高可用 |
| Topic / Queue | 逻辑主题 / 物理队列 |
| Producer Group / Consumer Group | 生产与消费身份；集群消费时组内分担队列 |

---

## 消息顺序如何保证？

RocketMQ 顺序分两层：

1. **分区有序（推荐）**  
   - 发送时对同一业务键（如订单号）选型同一 Queue（`MessageQueueSelector` / hash）。  
   - 消费使用 **顺序消费者**（`MessageListenerOrderly`），对同一队列加锁串行消费。  
   - 结果：同一业务键有序，不同键可并行。

2. **全局有序**  
   - Topic 只有一个 Queue，吞吐差，少用。

注意：

- 并发消费（`MessageListenerConcurrently`）**不保证**顺序。  
- 顺序消费时，某条失败会阻塞该队列后续消息 → 要控制耗时与失败处理，避免整队堵住。  
- 扩容 Queue 数量会改变 hash 映射，可能影响「历史键」与新队列的对应关系，变更需谨慎。

---

## 事务消息是什么？怎么保证最终一致？

典型场景：本地 DB 事务与「发 MQ」要同成同败（如下单写库 + 发下游消息）。

**半消息流程（高频）：**

1. Producer 发 **Half Message（半消息）** 到 Broker，对下游消费者不可见。  
2. 执行本地事务（写订单库等）。  
3. 根据本地结果 **Commit / Rollback** 半消息。  
4. 若 Broker 一直收不到最终确认，会 **回查** Producer 的本地事务状态（`TransactionListener.checkLocalTransaction`），再决定提交或回滚。

要点：

- 解决的是 **本地事务与发消息** 的最终一致，不是分布式多库 2PC 全家桶。  
- 下游仍要 **幂等**（Commit 后重复投递、消费重试仍可能发生）。  
- 回查接口必须可靠、可判定事务状态（建议事务状态落库）。

对比：Kafka 事务偏「多分区原子写」；RocketMQ 事务消息偏「业务本地事务 + 可靠投递」。

---

## 延迟消息 / 定时消息怎么做？

RocketMQ 原生支持 **延迟消息**（开源版多为固定延迟级别，如 1s、5s、…、2h）：

- 发送时设置 `delayTimeLevel`（或新版本定时投递 API，视版本）。  
- Broker 到期后再投递给消费者。  

常见用途：订单超时关单、重试退避、延迟校验。

注意：

- 开源版延迟级别固定，不是任意毫秒；任意定时看发行版/云产品能力或自建。  
- 大量延迟消息会占调度与存储，需评估级别与量级。

---

## 消费者组与负载均衡（类似 Rebalance）

- **集群消费（Clustering）**：同一 Consumer Group 内，队列均分到多个实例；一个 Queue 同一时刻基本由组内一个消费者处理。  
- **广播消费（Broadcasting）**：组内每个实例都收到全量消息。  

**再均衡触发**：消费者上下线、Queue 数量变化、部分实例挂掉等。客户端会重新分配 Queue（AllocateMessageQueue 策略）。

影响与应对：

- 再均衡瞬间可能重复消费或短暂暂停 → **幂等** + 合理超时。  
- 顺序消费时分配变化要特别小心，避免同队列被并发抢走（客户端有队列锁机制，仍需理解模型）。  
- 实例数远大于 Queue 数时，多余消费者空闲（类似 Kafka 消费者多于分区）。

## 消息积压怎么处理？

1. **看指标**：`Diff`（生产位点 - 消费位点）、Broker/Consumer TPS、耗时。  
2. **定位**：生产突增、消费变慢、个别队列热点、重试风暴、死循环失败。  
3. **扩容**：加消费者（≤ Queue 数有意义）；长期不够 **扩 Topic 读写队列数**（需评估顺序键映射）。  
4. **优化消费**：批量、异步下游、本地线程池、减少同步 RPC；慢消息隔离。  
5. **重试/死信**：失败进重试队列，耗尽进 **%DLQ%ConsumerGroup**，人工或专用修复。  
6. **应急**：临时跳过毒消息；开关降级非核心订阅；生产限流。

---

## 怎样避免重复消费？

RocketMQ 常见是 **至少一次**：超时、重试、Rebalance、ACK 丢失都可能导致重复。

手段：

- 业务 **幂等**（唯一键、状态机、Redis/DB 去重）。  
- 消费成功再 ACK（Push 下正常返回；异常会重投）。  
- 可用 Message Key / uniqKey 做辅助，但 **不能替代业务幂等**。  
- 注意顺序消费失败导致的反复投递。

---

## 消费失败怎么办？

- **并发消费**：失败返回后按策略进 **重试队列**（延迟级别递增），超过 `maxReconsumeTimes` 进 **死信队列**。  
- **顺序消费**：失败会阻塞队列，需谨慎抛异常；可业务侧记失败转异步，避免长期堵队列。  
- 监控消费失败 TPS、死信堆积；死信要有人工或补偿任务。

---

## 怎样避免消息丢失？

**生产端：**

- 同步发送并判断 SendResult；失败重试；重要消息可落本地/DB 补偿。  
- 刷盘与复制：`SYNC_FLUSH` / 同步复制更安全、更慢；异步更快点，故障窗口丢数风险更高。  

**Broker：**

- 主从 / DLedger；磁盘与高可用配置。  

**消费端：**

- 处理成功后再 ACK；不要「先 ACK 再异步慢慢处理」却不管失败。  

**事务消息：** 本地事务与投递绑定，减少「库写了但消息没出去」。

---

## 同步发、异步发、单向发？

| 方式 | 特点 | 场景 |
|------|------|------|
| 同步 | 有结果，可靠性高 | 重要订单、要强反馈 |
| 异步 | 吞吐高，回调感知成败 | 大多数在线业务 |
| Oneway | 不管结果，最快 | 日志类、可丢可补 |

---

## Tag、Key、过滤怎么用？

- **Tag**：同一 Topic 下业务子类型，Broker 可用 Tag 过滤，减少无用拉取。  
- **Key**：业务主键，便于控制台查询、哈希路由辅助。  
- SQL92 过滤等能力视版本；过滤条件过复杂可能增加 Broker 负担。

---

## 推模式 vs 拉模式？

- 对外多为 **Push**（客户端内部仍是长轮询拉）。  
- 长轮询：无消息时 Broker 挂起请求，有消息或超时再返回 → 兼顾实时与空转。

---

## 高可用怎么做？

- NameServer 多实例。  
- Broker 主从同步；DLedger 基于 Raft 选主（视版本/部署）。  
- 多机房需评估复制延迟与切换策略。  
- 消费组多实例防单点。

---

## RocketMQ vs Kafka（常考）

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| 定位 | 业务消息中心更强 | 日志/流平台更强 |
| 顺序 | Queue + 顺序消费 | Partition 内有序 |
| 事务消息 | 半消息+回查，偏业务 | 事务 Producer，偏链路 EOS |
| 延迟消息 | 原生支持（级别） | 基本靠自建 |
| 积压与重试 | 重试队列 + DLQ 成熟 | 多靠应用/框架 |
| 吞吐 | 高 | 通常极高，大数据生态强 |
| 运维 | NameServer+Broker | ZK/KRaft+Broker |

## 水平扩容（面试专题）

RocketMQ 水平扩展靠 **Broker 集群 + Topic 读写队列（Queue）**，不是 Kafka 那种全局分区槽。

### 扩展模型

```text
Topic
  ├─ 写队列 Q0..Qn-1   （Producer 轮询 / 选择队列）
  └─ 读队列（通常与写队列对应）
Consumer Group：队列在组内分配给各 Consumer 实例
有效消费并行 ≤ 该 Topic 的队列数
```

| 扩容动作 | 扩什么 | 注意 |
|----------|--------|------|
| **加 Broker** | 集群吞吐与存储 | 需规划 Topic 分布在哪些 Broker |
| **增加读写队列数** | 并行度 | **需改 Topic 配置**；历史消息仍在旧队列 |
| **加 Consumer** | 消费速度 | **> 队列数则空闲** |
| **主从 / DLedger** | HA，不直接扩写并行 | 主承担写，从同步 |

### 扩队列 vs 扩 Consumer

- 消费慢、Consumer 数 < 队列数 → **先加 Consumer**。  
- Consumer 已等于队列数仍慢 → **扩队列**（`writeQueueNums` / `readQueueNums`）+ 加 Consumer。  
- 顺序消息：同业务键进同 Queue；**扩队列会改变 hash 映射**，要谨慎。

### 与 Kafka 对比

| | RocketMQ | Kafka |
|--|------------|-------|
| 并行单元 | Queue | Partition |
| 扩并行 | 扩 Queue + Consumer | 扩 Partition + Consumer |
| 消费 > 并行单元 | Consumer 空闲 | 同左 |
| 路由 | 队列选择 / 业务 Key | Partition key hash |

### 扩容注意

- NameServer 轻量，通常 **多实例** 即可，不是瓶颈。  
- 跨 Broker 迁移主题较 **运维向**，需平台化均衡 Topic。  
- 磁盘与 commitlog 顺序写；加 Broker 要均衡 Topic 分布，防单机热点。

**30 秒收口：** RocketMQ 水平扩 = **加 Broker + 扩 Topic 队列数 + 加 Consumer（≤队列数）**；顺序场景扩队列要评估 Key 路由；HA 靠主从/DLedger，不等于写并行翻倍。

---

## 面试速答清单

- **顺序**：同键进同 Queue + 顺序消费；全局单 Queue。  
- **事务**：半消息 → 本地事务 → Commit/Rollback → 回查。  
- **延迟**：`delayTimeLevel` / 定时消息。  
- **再均衡**：组内按 Queue 分配；上下线触发；靠幂等。  
- **积压**：看 Diff → 优化消费 → 加实例/扩队列 → 治死信。  
- **水平扩容**：扩 Queue + Consumer（≤队列）；加 Broker。  
- **丢/重**：同步落盘复制 + 正确 ACK；重复靠幂等。
