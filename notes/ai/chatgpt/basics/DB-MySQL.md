# MySQL / InnoDB 面试笔记

面向面试口述：架构 → 写路径 → MVCC → 锁与隔离级别 → 索引 → 高可用与扩容。默认引擎按 **InnoDB** 答。

---

## 架构：一层怎么画？

```text
Client (JDBC / 代理)
    ↓
Server 层
  ├─ 连接器 / 线程
  ├─ 解析器（语法）
  ├─ 优化器（执行计划、选索引）
  └─ 执行器
    ↓
存储引擎层（InnoDB）
  ├─ Buffer Pool（页缓存）
  ├─ Redo Log / Undo Log
  ├─ 锁管理、事务、MVCC
  └─ 表空间文件（.ibd：聚簇索引 + 二级索引）
```

| 层 | 职责 |
|----|------|
| **Server** | SQL、权限、优化、视图/存储过程；**与引擎解耦** |
| **InnoDB** | 事务、行锁、MVCC、崩溃恢复、真正读写数据页 |
| **对比 MyISAM** | MyISAM 无事务/行锁/崩溃安全；线上业务几乎都用 InnoDB |

**面试一句话：** MySQL 是 Server + 可插拔引擎；并发与持久化细节在 InnoDB。

## 写数据原理（高频必画）

### 整体链路（更新一行）

```text
1. 执行器找引擎更新某行
2. 引擎：页不在内存 → 从磁盘读入 Buffer Pool
3. 先写 Undo（旧版本，供回滚 / MVCC）
4. 改 Buffer Pool 中的数据页（内存改，变脏页）
5. 写 Redo Log（Prepare / 记录物理变更），先保证崩溃可恢复
6. 写 Binlog（Server 层逻辑日志，复制/恢复用）
7. Commit：Redo 标记 commit；事务提交
8. 脏页稍后由后台刷盘（checkpoint），不是提交时立刻落盘整页
```

**关键认知：**

- **提交时保证的是日志落盘（Redo + Binlog）**，不是整表数据文件立刻刷完。  
- **Buffer Pool** 是性能核心：读写都先走内存页。  
- **刷脏** 异步：LRU、checkpoint、`innodb_flush_log_at_trx_commit` 等影响耐久与吞吐。

### Redo / Undo / Binlog 分工

| 日志 | 层级 | 记什么 | 干什么 |
|------|------|--------|--------|
| **Redo Log** | InnoDB | 页级物理变更（可循环写） | 崩溃恢复：重放未刷脏的修改 |
| **Undo Log** | InnoDB | 旧版本行 | 事务回滚 + **MVCC 读旧版本** |
| **Binlog** | Server | 逻辑变更（Statement/Row/Mixed） | 主从复制、时间点恢复（PITR） |

### 两阶段提交（Redo + Binlog 一致）

```text
Prepare（Redo prepare） → 写 Binlog → Commit（Redo commit）
```

- 只有 Redo、没有 Binlog：崩溃恢复后主从/备份不一致。  
- 面试：**两阶段提交保证 InnoDB 与 Binlog「同成功或同失败」**，主从数据才能对齐。

### `innodb_flush_log_at_trx_commit` / `sync_binlog`（常考）

| 参数 | =1（最安全） | 其它值 |
|------|--------------|--------|
| `innodb_flush_log_at_trx_commit` | 每次提交刷 Redo | 0/2 吞吐高，宕机可能丢最近事务 |
| `sync_binlog` | 每次提交刷 Binlog | 0 依赖 OS 刷盘，可能丢 |

金融级常 **双 1**；高吞吐可权衡。

### Change Buffer（别再叫错 Insert Buffer）

- **InnoDB**：非唯一二级索引的变更可先记在 **Change Buffer**，合并后再写二级索引页，减少随机 IO。  
- **不是** MyISAM 的 Insert Buffer；唯一索引、主键聚簇更新一般不能靠 Change Buffer 偷懒。  
- 面试答：**随机写二级索引 → Change Buffer 合并刷盘，降随机 IO。**

### Buffer Pool 要点

- 按 **页（默认 16KB）** 缓存数据与索引。  
- **LRU**（改进：young/old 区防全表扫污染）。  
- 脏页 + flush list；checkpoint 推进可回收 Redo。

## MVCC 原理（可重复读核心）

### 是什么？

**Multi-Version Concurrency Control**：一行保留多个版本，**读不阻塞写、写不阻塞读**（普通 SELECT = 快照读）。  
InnoDB 靠 **隐藏列 + Undo 版本链 + ReadView** 实现。

### 行隐藏列（纠正常见误区）

| 隐藏列 | 含义 |
|--------|------|
| **DB_TRX_ID** | 最近修改该行的事务 ID |
| **DB_ROLL_PTR** | 指向 Undo 中上一版本（版本链） |
| **DB_ROW_ID** | 无主键且无非空唯一键时，InnoDB 隐式生成的行号作聚簇键 |

没有所谓「DB_MIX_ID」；版本靠 **trx_id + undo 链**。

### 快照读 vs 当前读

| 类型 | SQL 例 | 行为 |
|------|--------|------|
| **快照读** | 普通 `SELECT` | 按 ReadView 看历史版本，**不加行锁**（RR/RC） |
| **当前读** | `SELECT … FOR UPDATE` / `LOCK IN SHARE MODE`、`UPDATE/DELETE` | 读**最新已提交**版本并加锁 |

### ReadView（可见性判断）

事务做快照读时生成/使用 ReadView，核心字段口述：

| 字段 | 含义 |
|------|------|
| `m_ids` | 创建视图时，**尚未提交**的活跃事务 ID 列表 |
| `min_trx_id` | 活跃事务中最小 ID |
| `max_trx_id` | 系统将要分配给下一事务的 ID（上界） |
| `creator_trx_id` | 创建该视图的事务自己的 ID |

**行版本是否可见（简化规则）：**

1. 行的 `trx_id == creator` → 自己改的，可见。  
2. `trx_id < min_trx_id` → 创建视图前已提交，可见。  
3. `trx_id >= max_trx_id` → 视图创建后才启动的事务，不可见。  
4. `min ≤ trx_id < max`：若 `trx_id` 仍在 `m_ids`（当时未提交）→ 不可见；否则已提交 → 可见。  
5. 不可见则沿 **DB_ROLL_PTR** 找 Undo 上一版本，再判，直到可见或没有。

### RR vs RC：ReadView 时机不同

| 隔离级别 | ReadView | 效果 |
|----------|----------|------|
| **RR（默认）** | 事务内**第一次**快照读创建，之后复用 | 可重复读；配合间隙锁防幻（当前读） |
| **RC** | **每次**快照读新建 ReadView | 能读到别的事务已提交的新版本 → 不可重复读 |

**面试收口：** MVCC = Undo 多版本 + ReadView 过滤；RR 用「一个视图贯穿」，RC 用「每句新视图」。

### Undo 与 purge

- UPDATE/DELETE 产生 Undo；旧版本挂在版本链上。  
- 没有任何事务再需要的历史版本，由 **purge** 线程清理。  
- Undo 膨胀常见原因：长事务不提交 → 历史版本不能清。

## 事务：ACID、脏读/幻读、隔离级别

### 脏读 / 不可重复读 / 幻读

| 现象 | 含义 | InnoDB 默认 RR |
|------|------|----------------|
| **脏读** | 读到未提交数据 | 不会（RC/RR） |
| **不可重复读** | 同一行两次读结果不同（被改） | MVCC 快照读可避免 |
| **幻读** | 范围两次读行数变（被插入） | 快照读多靠 MVCC；**当前读**靠 **间隙锁 / Next-Key** |

### 四级隔离（InnoDB 实现要点）

| 级别 | 脏读 | 不可重复读 | 幻读 | 实现要点 |
|------|------|------------|------|----------|
| RU | 可能 | 可能 | 可能 | 几乎直接读最新，极少用 |
| RC | 否 | 可能 | 可能 | 每次快照读新 ReadView；当前读写行锁 |
| **RR** | 否 | 否（快照） | 大部分控制 | 事务级 ReadView + Next-Key |
| Serializable | 否 | 否 | 否 | 普通 SELECT 升级为锁读 |

**纠正：** 不要说「锁算法 = MVCC」；**快照读靠 MVCC，写/当前读靠锁**，二者配合。

## 锁（行锁、间隙锁、死锁）

### InnoDB 有哪些锁？

| 锁 | 说明 |
|----|------|
| **S / X** | 共享读锁 / 排他写锁 |
| **Record Lock** | 锁住索引上的**记录** |
| **Gap Lock** | 锁住记录间**间隙**，防插入（幻读） |
| **Next-Key** | Record + 前面 Gap（默认 RR 范围当前读） |
| **意向锁** | 表级意向，加快「是否有人持行锁」判断 |
| **插入意向锁** | 插入前在间隙上的特殊锁，与 Gap 冲突检测 |

粒度口述：

- **行锁**：真正并发单位（基于索引记录；无索引可能退化为更多锁甚至表级效果）。  
- **表锁**：`LOCK TABLES`、或某些 DDL/元数据。  
- **页锁**：InnoDB 不对外主推「业务页锁」；锁信息在内存按记录管理。  
- **间隙锁**：RR 下范围条件当前读常见。

### 行锁怎么实现？

- **锁在索引记录上**，不是「表堆里的物理行号」这种直观模型。  
- 无合适索引 → 可能扫描更多记录并加更多锁。  
- 两阶段锁：加锁贯穿到事务结束再释放（简化口述）。

### 死锁

**何时：** 两事务交叉持锁等待（A 锁行1 等行2，B 锁行2 等行1）。

**检测：** InnoDB 等待图检测；`SHOW ENGINE INNODB STATUS`；错误日志。

**处理：** 回滚代价小的一方；业务侧统一加锁顺序、缩短事务、合理索引、避免大范围锁。

## 索引与 B+Tree

### 为什么用 B+Tree？

| 对比 | B-Tree | B+Tree（InnoDB） |
|------|--------|------------------|
| 数据位置 | 内部结点也可能有数据 | **仅叶子**存行/主键 |
| 扇出 | 相对小 | 内部只存键，**更矮** |
| 范围查 | 中序乱跳 | 叶子有序链表，顺序扫 |
| 点查 | 可能中途命中 | 路径稳定走到叶子 |

**优点口述：** 矮树少 IO、范围友好、页与 Buffer Pool 契合、二级索引可覆盖（叶子存键+主键）。

### 聚簇 vs 二级

```text
聚簇索引叶子 = 整行
二级索引叶子 = 二级键 + 主键 → 回表再走聚簇
```

### 哪些字段能走索引？

- 数值、字符串（可前缀）、日期、枚举等一般可建 B+Tree。  
- **失效常见：** 函数包列、隐式类型转换、`LIKE '%xx'`、最左前缀破坏、范围后列失效、OR 条件差等。  
- **全文** 另有 FULLTEXT，不是普通 B+Tree 等值。

| | 做法 |
|--|------|
| **乐观** | `version` / 时间戳：`UPDATE … WHERE id=? AND version=?`，影响行数=0 则冲突重试 |
| **悲观** | `SELECT … FOR UPDATE` 持锁再改；或表锁（少用） |

## 高可用与故障恢复

### 怎么做高可用？

| 方案 | 要点 |
|------|------|
| **主从复制** | Binlog → Relay；读写分离；异步/半同步 |
| **MGR** | 组复制，多数派，自动选主感更强 |
| **双活 / 多活** | 跨机房，冲突与延迟要设计 |
| **分片** | 单机写满后再水平拆（见下文） |

### 故障恢复原理

| 手段 | 作用 |
|------|------|
| **InnoDB 崩溃恢复** | Redo 重做 + Undo 回滚未提交 |
| **Binlog + 备份** | 时间点恢复、建从库 |
| **主从切换** | 主挂提升从；注意半同步/GTID 减少丢数 |

## 水平扩容（面试专题）

**结论：** 单机 InnoDB **垂直扩**有上限；**水平扩**靠读写分离、分库分表、或 TiDB/OceanBase。MySQL 自身不是原生无限写扩展。

| 方式 | 扩什么 | 写能否线性扩 | 手段 |
|------|--------|--------------|------|
| **读扩展** | 读 QPS | 写仍主库 | 主从 / MGR 读副本 |
| **分库分表** | 写+读 | 按片可以 | ShardingSphere、业务分片 |
| **NewSQL** | 写+读 | 自动分区 | TiDB、OceanBase |

```text
写 → 主库
读 → 从库 × N
```

- 读扩展改动小；**写瓶颈仍在主**；从库延迟读旧。  
- 分片键、全局 ID、跨片查询、扩容迁移是分库分表痛点。  
- TiDB/OceanBase：分区/Region 自动调度，SQL 更透明。

**30 秒：** 读用主从；写用分片或换分布式库；单机 InnoDB 加节点不会自动分区。

## OceanBase / TiDB 对比 MySQL（常考）

### OceanBase

- **OBServer** 存算一体 + 分区多副本共识；RootService 管元数据。  
- 优点：水平扩、强一致、多租户、MySQL 兼容；少做自建分库。

### TiDB

- **TiDB（无状态 SQL）+ TiKV（Raft）+ PD（调度/TSO）**；可选 TiFlash HTAP。  
- 优点：存算分离各自扩、Region 自动分裂、开源生态活跃。

| | 自建 MySQL 分片 | OB / TiDB |
|--|-----------------|-----------|
| 分片谁管 | 业务/中间件 | 引擎自动 |
| HA | 主从脚本 | 共识切主 |
| 适用 | 存量、团队熟 | 大库、不想扛分片 |

## 慢 SQL 排查（线上）

1. **发现：** slow log、Performance Schema、APM、`SHOW PROCESSLIST`。  
2. **计划：** `EXPLAIN` / `EXPLAIN ANALYZE`，看 type、key、rows、Extra。  
3. **索引：** 是否全表扫、回表过多、选择性差。  
4. **锁：** `innodb_trx`、`innodb_lock_waits`、死锁日志。  
5. **系统：** CPU、IO、`iostat`、连接数、临时表。  
6. **应用：** N+1、大事务、连接池、批量改小事务。

## 面试速记

| 主题 | 一句话 |
|------|--------|
| 架构 | Server 管 SQL；InnoDB 管事务/锁/页/日志 |
| 写路径 | 改 Buffer Pool → Undo → Redo → Binlog → 两阶段提交；脏页异步刷 |
| 三日志 | Redo 崩溃恢复；Undo 回滚+MVCC；Binlog 复制与备份 |
| MVCC | 隐藏列 + Undo 链 + ReadView；RR 视图复用，RC 每句新建 |
| 快照/当前读 | 普通 SELECT 快照；FOR UPDATE 等当前读加锁 |
| 锁 | 行锁在索引上；RR 用 Next-Key 控幻读 |
| B+Tree | 矮、叶子链表、范围友好；聚簇整行、二级回表 |
| 高可用 | 主从/MGR + Binlog；崩溃靠 Redo/Undo |
| 水平扩 | 读从库；写分片或 NewSQL |

**口述收口：** InnoDB 写是「日志先行 + 内存改页」；读并发靠 MVCC 多版本；隔离级别是 ReadView 策略 + 锁策略的组合。
