# Vibe Coding

Vibe Coding（氛围编程 / 感觉式编程）一般指：用自然语言描述意图，主要由 AI（Chat / Agent）生成与修改代码，人负责提需求、验收、纠偏，而不是逐行手写。

名字来自 Andrej Karpathy 等对「靠感觉驱动 AI 写代码」这一工作方式的概括；和「完全放手不管」不是一回事——面试里要强调 **人仍要对正确性、安全与可维护性负责**。

---

## 什么是 Vibe Coding？和传统写代码有什么区别？

| | 传统编码 | Vibe Coding |
|--|----------|-------------|
| 主操作 | 人手写代码 | 人写意图 / 约束，AI 产出代码 |
| 思维重心 | 语法、API、实现细节 | 问题拆解、验收标准、风险控制 |
| 反馈环 | 编译/跑测/自己改 | 对话 → 生成 → 跑通 → 再提示 |
| 风险 | 实现慢 | 幻觉、隐式假设、不可维护的「能跑」代码 |

一句话：**不是不写代码，而是把「实现」更多交给模型，把「规格与审查」留在人这边。**

---

## Vibe Coding 适合什么场景？不适合什么？

**适合：**

- CRUD、样板代码、脚本、正则、SQL、单测草稿
- 在熟悉技术栈里做中小改动、重构辅助、读不懂的遗留代码解释
- 探索 API、写 Demo、快速验证想法

**不适合或要强约束：**

- 安全敏感（鉴权、加密、支付、权限）
- 强正确性（并发协议、分布式一致性、金融计算）
- 缺少测试/无法运行验证的环境
- 需求极度模糊又要求一次交付生产代码

面试答法：能加速，但不能替代设计和 Review；越关键路径越要缩小 AI 的自主范围。

---

## 做好 Vibe Coding 的关键实践有哪些？

1. **先规格后代码**：输入/输出、边界、错误码、非功能（性能、幂等）先说清。
2. **小步提交**：一次只改一个模块；大改拆 PR。
3. **可验证**：能跑的测试、脚本、复现步骤一起要；没有验证等于没完成。
4. **给足上下文**：相关文件、接口约定、错误日志、技术栈版本；忌空泛「帮我优化一下」。
5. **强制 Review**：当别人写的代码看——正确性、安全、复杂度、命名、重复。
6. **用规则固化**：项目级 Rules / AGENTS.md / Lint / CI，减少每次重复叮嘱。
7. **版本可控**：Git 清晰；AI 大改前先分支，方便回滚。

## 和 Copilot、Chat、Agent 有什么区别？

| 形态 | 特点 | 典型用法 |
|------|------|----------|
| 补全型（Copilot 等） | 光标处续写，上下文窗口相对局部 | 写函数、补样板 |
| Chat 问答 | 多轮讨论，人粘贴代码/文件 | 问方案、改片段 |
| Agent | 可多文件编辑、跑命令、迭代修错 | 端到端实现小功能 |

Vibe Coding 常落在 **Chat / Agent** 上：用对话驱动整段功能，而不是只靠单行补全。

---

## AI 写的代码常见坑有哪些？怎么防？

- **幻觉**：不存在的 API、错误的配置项、过时的写法 → 以官方文档/本仓库代码为准，让 AI 引用现有符号。
- **表面正确**：Happy path 能跑，边界/并发/失败重试没有 → 要测试用例清单。
- **过度工程**：乱加抽象、无用配置 → 要求「最小改动」「禁止无关重构」。
- **安全漏洞**：SQL 拼接、命令注入、密钥进仓库、关闭校验 → 安全清单必查。
- **静默破坏**：改了你没点名的文件/行为 → diff 全看，禁止「顺便」。
- **许可证与隐私**：把专有代码/密钥贴进公有模型 → 遵守公司数据策略。

## 如何 Review AI 生成的代码？（面试加分）

按层检查：

1. **需求**：是否只做了要求的事？有没有自作主张？
2. **正确性**：边界、空值、错误处理、事务/幂等。
3. **安全**：输入校验、鉴权、敏感数据、依赖来源。
4. **性能**：N+1、无界内存、锁粒度、多余 IO。
5. **可维护**：命名、重复、与项目风格一致；能否删掉一半抽象。
6. **可观测**：日志、指标、失败是否可诊断。
7. **测试**：单测/集成测是否真覆盖关键分支。

原则：**AI 生成 ≠ 可合并**；你是 Author，要对 diff 负责。

## Prompt 怎么写更有效？

差：`帮我写个用户服务`  
好：`在现有 Spring Boot 3.2 项目中，新增 GET /api/users/{id}：从 UserRepository 查，不存在返回 404；复用 GlobalExceptionHandler；不要改其他模块；补 2 个单测。`

结构模板：

```text
目标：…
约束：技术栈 / 目录 / 不要动的文件
现状：相关类名、错误现象、日志
验收：命令怎么跑、期望输出
风格：跟随仓库现有写法，最小 diff
```

迭代时：**贴报错原文**，说明「只修这个错，别重构」。

---

## 如何衡量 Vibe Coding 的产出质量？

不要只看「生成速度」，看：

- 一次通过率（是否反复返工）
- Review 打回原因分布（需求理解 / 缺陷 / 风格）
- 线上缺陷与回滚
- 测试覆盖与 CI 绿灯
- 个人是否仍理解改动（说不清实现 = 风险）

---

## 团队落地要注意什么？

- **规范**：哪些模块允许 Agent 改；密钥与生产数据禁止进提示词。
- **工具**：统一 IDE / 模型 / 私有化策略；MCP、知识库只接审批过的源。
- **流程**：AI 辅助的 PR 同样要测要审；可要求说明「哪些是 AI 生成、如何验证」。
- **能力建设**：培训「写清规格 + Review」，避免变成「粘贴工程师」。
- **知识产权**：确认代码助手协议与公司合规。

---

## Vibe Coding 会取代工程师吗？

标准答法：

- 取代的是 **重复劳动和检索成本**，不是系统设计、业务权衡、责任归属。
- 工程师重心上移：问题定义、架构、质量、协作。
- 不会用 AI 的人会被会用的人卷；只会用 AI 而不会验证的人会被事故卷。

---

## 和「结对编程」「低代码」的关系？

- **结对**：Vibe Coding 像「人 + AI 结对」；AI 速度快但不具备共同责任意识。
- **低代码**：低代码是平台封装；Vibe Coding 仍产出通用代码，灵活性高、规范靠人。

---

## 口述题：讲一次你用 AI 高效完成需求的经历

建议 STAR：

1. **情境**：需求与截止时间。
2. **任务**：你负责哪块。
3. **行动**：如何拆任务、写提示、跑测、纠错、Review。
4. **结果**：耗时、质量、踩过的坑（幻觉/漏测）和下次改进。

避免只说「我让 GPT 写了」；要体现 **控制与验证**。

## 在 Cursor 里有没有配 MCP 或其他方式提效？（高频实操题）

面试官想听的是：**不只会聊天写码，还会把 IDE / 工具链进 Agent**，减少复制粘贴和上下文丢失。

### MCP 是什么？为什么提效？

**MCP（Model Context Protocol）**：给 AI 接「外部工具/数据源」的标准协议。在 Cursor 里配置 MCP Server 后，Agent 可在对话中直接调工具（查库、查文档、查工单、跑浏览器等），而不用你手动把结果粘进聊天框。

| 常见 MCP 方向 | 提效点 |
|---------------|--------|
| 数据库（Postgres/MySQL 等） | 让 Agent 查表结构、样例数据，写 SQL/改 Entity 更准 |
| 浏览器 / Playwright | 验证页面、抓控制台错误，闭环修前端 |
| GitHub / GitLab | 读 Issue、PR、CI 失败日志，对着修 |
| Jira / Linear / Notion | 拉需求描述，少切窗口 |
| 内部文档 / Wiki / 向量库 | 搜公司规范、接口文档 |
| 监控（Sentry、日志平台等） | 带着真实报错上下文改代码 |
| 文件系统 / 专用 API | 封装重复运维或查询动作 |

**配置要点（口述即可）：**

- 在 Cursor 的 MCP 设置里加 Server（本地命令或远程 URL），按需填环境变量（连接串、Token）。
- **最小权限**：只读库、只读 Issue；生产写权限慎开。
- **密钥不进仓库**：用本机/团队密钥管理，不把 Token 写进规则文件提交。
- 先验证工具列表能刷出来，再在 Agent 里明确「用某某 MCP 查…」。

**答法示例：**  
“配过数据库和文档类 MCP，改接口时让 Agent 自己对一下表结构和现有 API 文档，减少幻觉；接过 Issue/CI，修 bug 时直接带失败日志。原则是只读优先、密钥外置、工具返回当上下文而不是当真理。”

### 除了 MCP，Cursor 里还有哪些提效方式？

按「投入小 → 收益稳」排列，面试可挑 3～5 条讲深：

**1. 项目规则（Rules / `.cursor/rules` / AGENTS.md）**  
把技术栈、目录约定、禁止事项、Code Review 清单写成规则，**每次对话自动带上**，少重复叮嘱「别乱重构、跟现有风格」。  
例：Java 项目规定包结构、禁止引入新框架、单测必须可跑。

**2. Skills / 自定义技能**  
把高频流程固化成技能（发 PR、写迁移、对一下接口规范），一句话触发完整步骤，比每次从零 prompt 稳。

**3. Hooks（钩子）**  
在 Agent 提交提示、改文件、跑 Shell、调 MCP 前后插检查：例如禁止碰 `.env`、危险命令二次确认、改完跑格式化。偏「护栏」，防 Vibe Coding 跑飞。

**4. 准确喂上下文（比盲目开 MCP 更重要）**  
- `@文件` / `@目录` / `@Codebase`：缩小检索范围  
- `@Docs`：索引官方文档或内部文档 URL，减少过时 API  
- 选中代码再问、贴报错原文、说明「最小 diff」  

**5. 模式分工**  
- **Ask**：只读探查，适合先搞懂再改  
- **Agent**：多文件实现、跑命令修错  
- **手动改关键路径 + Agent 干样板**：安全/支付模块收紧自主权  

**6. 终端与验证闭环**  
允许 Agent 跑测试 / lint / 启动应用；「生成 → 跑红 → 再改」比纯聊天粘贴快一个数量级。没有验证的生成不算提效。

**7. Notepad / 备忘与任务拆解**  
长需求先写成验收清单，再分多次 Agent 任务，避免一次对话塞整系统。

**8. 团队共享**  
规则、推荐 MCP 列表、禁止项进仓库或内部文档；新人开箱同一套约束，避免每人一套「玄学 prompt」。

### 怎么讲「提效」才不显得虚？

用对比说话：

| 以前 | 配了 MCP / Rules 之后 |
|------|------------------------|
| 自己开库客户端抄表结构贴进 Chat | Agent 只读查 schema 再写代码 |
| 每次重复「我们用 Java 17 + 禁止某某」 | Rules 自动注入 |
| CI 红了来回切网页复制日志 | GitHub/CI MCP 或日志直接喂给 Agent 修 |
| AI 乱改无关文件 | Rules + Review + Hook 限制 |

也要主动说边界：**MCP 返回也会错/过期**；写库、发生产、碰密钥必须人确认；提效度量看「返工次数、一次 PR 通过率」，不看「生成了多少行」。

### 口述题：你在开发中如何用 Cursor 提效？

可套：

1. **规则**：项目 Rules 固定栈与最小改动原则。  
2. **MCP**：1～2 个高价值只读源（库表 / 文档 / Issue）。  
3. **闭环**：Agent 改完跑测试；失败日志继续喂。  
4. **Review**：安全与核心逻辑必看 diff。  
5. **结果**：某次需求从 X 天到 Y 小时，但补了哪些单测、踩过什么幻觉。

## 速记

| 问题 | 一句话 |
|------|--------|
| 是什么 | 自然语言驱动，AI 写码，人定规格与验收 |
| 价值 | 提速样板与探索；不替代设计与责任 |
| 风险 | 幻觉、假正确、安全、不可维护 |
| 做法 | 小步、可测、强 Review、规则固化 |
| 工具差 | 补全局部；Chat 方案；Agent 多文件闭环 |
| Cursor 提效 | MCP 接外部上下文；Rules/Skills/Hooks 护栏；@ 精准喂料；测试闭环 |
| MCP 原则 | 只读优先、密钥外置、工具结果要校验 |
| 团队 | 合规、规范、同等 PR 质量门禁 |
