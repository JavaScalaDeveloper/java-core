# Vibe Coding

Vibe Coding（氛围编程 / 感觉式编程）一般指：用自然语言描述意图，主要由 AI（Chat / Agent）生成与修改代码，人负责提需求、验收、纠偏，而不是逐行手写。

名字来自 Andrej Karpathy 等对「靠感觉驱动 AI 写代码」这一工作方式的概括；和「完全放手不管」不是一回事——面试里要强调 **人仍要对正确性、安全与可维护性负责**。

---

## 什么是 Vibe Coding？和传统写代码有什么区别？

| | 传统编码 | Vibe Coding |
|--|----------|-------------|
| 主操作 | 人手写代码 | 人写意图 / 约束，AI 产出代码 |
| 思维重心 | 语法、API、实现细节 | 问题拆解、验收标准、风险控制 |
| 反馈环 | 编译/跑测/自己改 | 对话 → 生成 → 跑通 → 再提示 |
| 风险 | 实现慢 | 幻觉、隐式假设、不可维护的「能跑」代码 |

一句话：**不是不写代码，而是把「实现」更多交给模型，把「规格与审查」留在人这边。**

---

## Vibe Coding 适合什么场景？不适合什么？

**适合：**

- CRUD、样板代码、脚本、正则、SQL、单测草稿
- 在熟悉技术栈里做中小改动、重构辅助、读不懂的遗留代码解释
- 探索 API、写 Demo、快速验证想法

**不适合或要强约束：**

- 安全敏感（鉴权、加密、支付、权限）
- 强正确性（并发协议、分布式一致性、金融计算）
- 缺少测试/无法运行验证的环境
- 需求极度模糊又要求一次交付生产代码

面试答法：能加速，但不能替代设计和 Review；越关键路径越要缩小 AI 的自主范围。

---

## 做好 Vibe Coding 的关键实践有哪些？

1. **先规格后代码**：输入/输出、边界、错误码、非功能（性能、幂等）先说清。
2. **小步提交**：一次只改一个模块；大改拆 PR。
3. **可验证**：能跑的测试、脚本、复现步骤一起要；没有验证等于没完成。
4. **给足上下文**：相关文件、接口约定、错误日志、技术栈版本；忌空泛「帮我优化一下」。
5. **强制 Review**：当别人写的代码看——正确性、安全、复杂度、命名、重复。
6. **用规则固化**：项目级 Rules / AGENTS.md / Lint / CI，减少每次重复叮嘱。
7. **版本可控**：Git 清晰；AI 大改前先分支，方便回滚。

## 和 Copilot、Chat、Agent 有什么区别？

| 形态 | 特点 | 典型用法 |
|------|------|----------|
| 补全型（Copilot 等） | 光标处续写，上下文窗口相对局部 | 写函数、补样板 |
| Chat 问答 | 多轮讨论，人粘贴代码/文件 | 问方案、改片段 |
| Agent | 可多文件编辑、跑命令、迭代修错 | 端到端实现小功能 |

Vibe Coding 常落在 **Chat / Agent** 上：用对话驱动整段功能，而不是只靠单行补全。

## AI 写的代码常见坑有哪些？怎么防？

- **幻觉**：不存在的 API、错误的配置项、过时的写法 → 以官方文档/本仓库代码为准，让 AI 引用现有符号。
- **表面正确**：Happy path 能跑，边界/并发/失败重试没有 → 要测试用例清单。
- **过度工程**：乱加抽象、无用配置 → 要求「最小改动」「禁止无关重构」。
- **安全漏洞**：SQL 拼接、命令注入、密钥进仓库、关闭校验 → 安全清单必查。
- **静默破坏**：改了你没点名的文件/行为 → diff 全看，禁止「顺便」。
- **许可证与隐私**：把专有代码/密钥贴进公有模型 → 遵守公司数据策略。

## 如何 Review AI 生成的代码？（面试加分）

按层检查：

1. **需求**：是否只做了要求的事？有没有自作主张？
2. **正确性**：边界、空值、错误处理、事务/幂等。
3. **安全**：输入校验、鉴权、敏感数据、依赖来源。
4. **性能**：N+1、无界内存、锁粒度、多余 IO。
5. **可维护**：命名、重复、与项目风格一致；能否删掉一半抽象。
6. **可观测**：日志、指标、失败是否可诊断。
7. **测试**：单测/集成测是否真覆盖关键分支。

原则：**AI 生成 ≠ 可合并**；你是 Author，要对 diff 负责。

## Prompt 怎么写更有效？

差：`帮我写个用户服务`  
好：`在现有 Spring Boot 3.2 项目中，新增 GET /api/users/{id}：从 UserRepository 查，不存在返回 404；复用 GlobalExceptionHandler；不要改其他模块；补 2 个单测。`

结构模板：

```text
目标：…
约束：技术栈 / 目录 / 不要动的文件
现状：相关类名、错误现象、日志
验收：命令怎么跑、期望输出
风格：跟随仓库现有写法，最小 diff
```

迭代时：**贴报错原文**，说明「只修这个错，别重构」。

## 如何衡量 Vibe Coding 的产出质量？

不要只看「生成速度」，看：

- 一次通过率（是否反复返工）
- Review 打回原因分布（需求理解 / 缺陷 / 风格）
- 线上缺陷与回滚
- 测试覆盖与 CI 绿灯
- 个人是否仍理解改动（说不清实现 = 风险）

---

## 团队落地要注意什么？

- **规范**：哪些模块允许 Agent 改；密钥与生产数据禁止进提示词。
- **工具**：统一 IDE / 模型 / 私有化策略；MCP、知识库只接审批过的源。
- **流程**：AI 辅助的 PR 同样要测要审；可要求说明「哪些是 AI 生成、如何验证」。
- **能力建设**：培训「写清规格 + Review」，避免变成「粘贴工程师」。
- **知识产权**：确认代码助手协议与公司合规。

---

## Vibe Coding 会取代工程师吗？

标准答法：

- 取代的是 **重复劳动和检索成本**，不是系统设计、业务权衡、责任归属。
- 工程师重心上移：问题定义、架构、质量、协作。
- 不会用 AI 的人会被会用的人卷；只会用 AI 而不会验证的人会被事故卷。

---

## 和「结对编程」「低代码」的关系？

- **结对**：Vibe Coding 像「人 + AI 结对」；AI 速度快但不具备共同责任意识。
- **低代码**：低代码是平台封装；Vibe Coding 仍产出通用代码，灵活性高、规范靠人。

---

## 口述题：讲一次你用 AI 高效完成需求的经历

建议 STAR：

1. **情境**：需求与截止时间。
2. **任务**：你负责哪块。
3. **行动**：如何拆任务、写提示、跑测、纠错、Review。
4. **结果**：耗时、质量、踩过的坑（幻觉/漏测）和下次改进。

避免只说「我让 GPT 写了」；要体现 **控制与验证**。
