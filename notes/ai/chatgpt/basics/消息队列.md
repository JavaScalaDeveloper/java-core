# Kafka

## Kafka 消息队列的架构

Kafka 是一个高吞吐量、分布式的消息队列 / 流平台，核心组件如下：

- **Topic（主题）**：消息的逻辑分类；一个 Topic 可拆成多个 Partition。
- **Producer（生产者）**：向指定 Topic 发消息，可指定分区或按 Key 路由。
- **Consumer（消费者）**：订阅 Topic 消费；通常以 **Consumer Group** 部署，组内分担分区。
- **Broker**：集群中的服务节点，负责存储与转发；多个 Broker 组成集群。
- **Partition（分区）**：并行与扩展的基本单位；分区内消息有序；可配置多副本。
- **Leader / Follower**：分区多副本中，Leader 负责读写，Follower 同步；Leader 故障可切换。
- **ZooKeeper / KRaft**：老版本用 ZK 做元数据与 Controller 选举；新版本走向 **KRaft**（内建 Raft 元数据）。
- **Offset（偏移量）**：分区内消息位移；消费者用 Offset 记录消费进度。

架构特点：高吞吐、可水平扩展、副本容错、磁盘持久化可回溯、多消费组独立订阅（发布-订阅）。

一句话串起来：**Topic 按 Partition 并行，Partition 内有序；Producer 写 Leader，Follower 同步；Consumer Group 内每个 Partition 同一时刻只被一个消费者消费，靠 Offset 记进度。**

| 概念 | 作用 |
|------|------|
| Topic | 逻辑主题 |
| Partition | 物理并行单元，决定吞吐与局部顺序 |
| Offset | 消费进度指针 |
| Replica / ISR | 副本冗余；ISR 为与 Leader 同步的副本集 |
| Consumer Group | 水平扩展消费 |
| Coordinator | 管理组成员、分区分配、Rebalance |

---

## Kafka 怎样避免重复消费？

- **Offset**：按分区记录消费位置；重启可从提交点继续。
- **Consumer Group**：组内同一分区同一时刻只被一个消费者消费。
- **提交 Offset**：处理完成后提交；自动/手动提交时机不当仍可能重复。
- **分区内有序**：同分区顺序消费，不等于“绝不重复”。

**结论**：Kafka 常见是 **至少一次（At-Least-Once）**。故障、Rebalance、提交失败都可能导致重复 → **业务必须幂等**（唯一键、状态机、去重表）。Kafka Streams / 事务可做更强语义，但跨 DB 仍要幂等或事务方案。

---

## Kafka 怎样避免消息丢失？

**生产端：**

- `acks=all` + 合理 `min.insync.replicas`（如 RF=3 时至少 2）
- 开启 **幂等生产者**（`enable.idempotence=true`），配合 `retries`
- 需要跨分区原子写时用 **事务生产者**

**Broker 端：**

- 消息落盘（先 Page Cache，再刷盘策略）
- 多副本 + ISR；Leader 切换尽量在 ISR 内

**消费端：**

- **先处理成功再提交 Offset**；先提交后处理失败会造成“假丢”（其实是跳过）

极端情况下若允许 unclean leader election，可能丢未充分复制的数据。高可靠场景关闭 unclean 选举，用可用性换一致性。

---

## Kafka 怎样实现高可用？

- **多副本**：分区多副本跨 Broker；Leader 挂了从 ISR 选新 Leader
- **Controller**：管理分区 Leader/副本状态；故障可重选（ZK 或 KRaft）
- **ISR**：只有跟上的副本可升主，降低数据回退风险
- **元数据高可用**：ZK 集群或 KRaft Controller Quorum
- **水平扩展**：加 Broker / 分区提升吞吐
- **消费组重平衡**：成员变化时重新分配分区，保证组级可持续消费

---

## Kafka 的 ACK（生产者确认）

ACK 指 **生产者** 收到 Broker 对“写入成功”的确认（不是消费者 ACK）：

| acks | 含义 | 特点 |
|------|------|------|
| 0 | 发出即不管 | 最快，可能丢 |
| 1 | Leader 写入成功即确认 | 折中；Leader 崩且未复制时可能丢 |
| all/-1 | ISR 内满足同步要求后确认 | 最稳，延迟更高 |

配合：`acks=all` + `min.insync.replicas≥2` + 幂等/事务，才是生产环境常见“不丢”组合。

---

## Kafka 为什么快？（高频）

1. **顺序追加写磁盘**：Partition 日志顺序 append  
2. **OS Page Cache**：热数据走页缓存  
3. **零拷贝（sendfile）**：减少用户态拷贝  
4. **批量 + 压缩**：降低网络与磁盘开销  
5. **分区并行**：多分区多消费者并行  

面试落到：**顺序 IO + PageCache + 批量 + 零拷贝 + 分区并行**。

---

## Partition 数量怎么定？消息怎么分区？

分区越多吞吐上限越高，但文件句柄、内存、选举与 Rebalance 成本上升；**同组消费者数 > 分区数** 时多余消费者空闲。

分区策略：

- 指定 Partition  
- **按 Key 哈希** → 同 Key 同分区 → **局部有序**  
- 轮询 / Sticky（无 Key）

**全局有序**只能单分区（吞吐差）。业务多用订单号等业务键做局部有序。

---

## ISR、HW、LEO？Leader 挂了怎么选主？

- **LEO**：副本日志末端位移（下一条待写位置）  
- **HW（高水位）**：对消费者可见的最高位移（避免读到未充分复制数据）  
- **ISR**：与 Leader 保持同步的副本集合；落后过多会被踢出  

Leader 故障时在 ISR 中选举；`unclean.leader.election.enable=true` 可能选落后副本 → **可能丢数据换可用**。

---

## 三种投递语义 & Exactly-Once

| 语义 | 含义 | 典型做法 |
|------|------|----------|
| At-Most-Once | 最多一次，可能丢 | 先提交再处理；acks 过弱 |
| At-Least-Once | 至少一次，可能重复 | 先处理再提交；生产重试 |
| Exactly-Once | 精确一次 | 幂等/事务 + 输出也纳入事务，或业务幂等 |

Kafka EOS（幂等 + 事务）保证的是 **Kafka 内部链路** 的精确一次叙事；**不自动等于** 你写 MySQL 的 Exactly-Once。跨系统用：事务消息、本地消息表、幂等落库。

---

## Offset 提交：自动 vs 手动

| 方式 | 优点 | 风险 |
|------|------|------|
| 自动提交 | 简单 | 先提交后处理失败 → 丢；处理完未提交 → 重复 |
| 同步手动 | 可控 | 阻塞、吞吐下降 |
| 异步手动 | 吞吐好 | 要处理回调失败 |

推荐：**处理成功后再提交**；批处理可“处理一批再提交”，批内重复用幂等消化。

---

## Consumer Rebalance 与消息积压

**Rebalance 触发**：成员加减、订阅/分区变化、会话超时等。期间分区回收，消费暂停。

优化：合理 `max.poll.interval.ms` / `session.timeout.ms`；控制 `max.poll.records`；静态成员；协作式分配（Cooperative Sticky）降低停顿。

**积压（Lag）排查**：

1. 定位 Topic/分区 lag：生产突增还是消费变慢  
2. 消费侧：GC、慢 SQL、下游、线程池、反序列化  
3. 扩容：加消费者（≤分区数）、长期可加分区  
4. 降载 / 慎用重置 Offset  

---

## 日志清理：delete vs compact

- **delete**：按时间/大小删旧段（日志类）  
- **compact**：按 Key 保留最新值（changelog / 状态类）  

---

## ZooKeeper vs KRaft

| 维度 | ZooKeeper 模式 | KRaft |
|------|----------------|-------|
| 元数据 | 依赖 ZK | Broker 内建 Raft 元数据 |
| 运维 | 两套系统 | 更统一 |
| 趋势 | 老集群常见 | 新版本默认方向 |

---

## Kafka 面试速答：丢、重、乱、积压

- **丢**：生产 acks 弱；消费先提交后处理；unclean 选举  
- **重**：至少一次 + Rebalance/重试 → **幂等**  
- **乱**：跨分区无序；同分区多线程乱序处理  
- **积压**：消费慢或分区不够；先查 lag 再扩容/优化

# RocketMQ

## RocketMQ 消息队列的架构

RocketMQ 核心组件：**Producer、Consumer、Broker、NameServer**。

- **Producer**：发往 Topic；可同步/异步；可设延迟级别、Tag 等。  
- **Consumer**：订阅 Topic；Pull/Push；集群模式（组内分担）或广播模式。  
- **Broker**：存储与转发；按队列（Queue）划分；多副本高可用。  
- **NameServer**：路由与元数据；轻量，无强主从状态机（与 Kafka ZK/KRaft 不同）。

## RocketMQ 怎样避免重复消费？

- 消费组 + 消费进度（位点）管理  
- 消费成功后 ACK；未 ACK 会重试  
- MessageKey 等业务去重；**最终仍靠幂等**

## RocketMQ 怎样避免消息丢失？

- 同步刷盘 / 同步复制等持久化与副本策略（按级别权衡性能）  
- 发送超时重试、失败落库补偿  
- 消费完成后再 ACK，避免“未处理当成功”  
- 事务消息（半消息）用于本地事务与发消息的最终一致

## RocketMQ 怎样实现高可用？

- NameServer 多实例  
- Broker 主从 / Dledger 等复制与切换  
- 消费组负载均衡与故障转移  
- 水平扩展 Broker 与多队列并行

# Pulsar

## Pulsar 是什么？为什么说“计算存储分离”？

Apache Pulsar 是云原生分布式 **消息流平台**。核心是：

- **Broker**：协议接入、订阅、分发、负载均衡 —— 更偏 **无状态服务层**  
- **BookKeeper Bookie**：消息持久化（Ledger/Entry）—— **存储层**  
- **ZooKeeper / 元数据存储**：元数据与协调（新版本持续演进）

对比 Kafka「Broker 本地存日志」，Pulsar 把落盘下沉到 Bookie，**扩 Broker、故障转移**更轻；存储扩容则扩 Bookie。

## Pulsar 核心概念

| 概念 | 含义 |
|------|------|
| Tenant | 多租户顶层隔离 |
| Namespace | 策略单元（副本、retention、权限、TTL 等） |
| Topic | 消息通道；persistent / non-persistent |
| Partitioned Topic | 分区主题，提升并行 |
| Subscription | **订阅是一等公民**；Cursor（游标）在服务端 |

和 Kafka 最大体感差异：**Kafka 进度主要在 Consumer Group/Offset；Pulsar 订阅游标由服务端管理**，多种订阅模型原生支持。

## Pulsar 订阅模式（高频）

1. **Exclusive**：一订阅一消费者  
2. **Failover**：主备，主挂备上  
3. **Shared**：同订阅多消费者 **消息级竞争**（更像传统队列）  
4. **Key_Shared**：同 Key 到同一消费者，兼顾局部有序与并行  

Kafka Consumer Group 是 **分区级独占**；Pulsar Shared 可以是 **消息级分发**，队列语义更直接。

## Pulsar 存储、Cursor 与 Ack

- 写入 BookKeeper **Ledger**（段式日志）  
- 每个 Subscription 有 **Cursor**  
- 消费者 **Ack**（单个/累积）推进游标；未确认可重投  
- 支持 Nack / 超时重投，易做重试语义  

抓手：**服务端游标 + Ack = 消费进度权威在服务端**。

## Pulsar 如何保证不丢、如何看待重复？

**不丢（生产）**：写多 Bookie 法定人数（ensemble / write / ack quorum）；失败重试。  

**不丢（消费）**：未 Ack 不推进 cursor，宕机后重投未确认消息。  

**重复**：至少一次下仍可能重复 → **业务幂等**（与 Kafka 相同结论）。

## Pulsar 延迟消息、重试、死信

- 延迟 / 定时投递（按版本与 API）  
- Nack 或否定确认触发重投，可配延迟重试  
- **死信 Topic（DLQ）**：超过最大重试进入死信  

对比：Kafka 更偏日志流，延迟/重试/DLQ 多靠应用或上层框架；Pulsar 更接近“消息队列产品能力”。

## Pulsar 多租户、Function、IO、Schema（加分）

- **Tenant/Namespace**：同一集群服务多团队，策略隔离更产品化  
- **Pulsar Functions**：轻量事件处理  
- **Pulsar IO**：Source/Sink  
- **Schema**：Schema 管理与兼容  
- **Geo-replication / Tiered Storage**：跨机房复制、冷热分层常见考点  

优点：存储计算分离、订阅灵活、多租户好。代价：Broker + Bookie + 元数据，**运维组件更多**。

## Pulsar 面试速答

- 架构：Broker 无状态 + BookKeeper 存盘  
- 订阅：Exclusive / Failover / Shared / Key_Shared  
- 进度：服务端 Cursor + Ack  
- 可靠：写 quorum + 正确 Ack；重复靠幂等  
- 场景：云上多租户、队列+流统一、灵活订阅

# Pulsar vs Kafka（对比题）

## 一句话

- **Kafka**：分布式 **提交日志 / 流平台**，存储与 Broker 同体，流处理与大数据生态极强。  
- **Pulsar**：云原生 **消息流平台**，**Broker 与 BookKeeper 分离**，订阅与多租户更“队列产品化”。

## 对比表

| 维度 | Kafka | Pulsar |
|------|-------|--------|
| 存储 | Broker 本地日志段 | BookKeeper Bookie |
| Broker | 有状态（存数据） | 更偏无状态服务层 |
| 扩容 | 扩 Broker 常伴随数据均衡/迁移 | 扩 Broker 较轻；扩存储扩 Bookie |
| 消费进度 | Offset（Group 协调） | Subscription Cursor（服务端） |
| 并行模型 | 分区级；组内一分区一消费者 | 分区 + Shared 消息竞争 + Key_Shared |
| 顺序 | 分区内有序 | 分区 / Key 维度有序；Shared 不保证全局有序 |
| 多租户 | ACL + 命名约定 | Tenant / Namespace 原生 |
| 延迟 / 重试 / DLQ | 多靠应用层 | 产品能力更直接 |
| 生态 | Connect / Streams / 社区极大 | Function / IO；亦有 KoP 等兼容 Kafka 协议 |
| 运维 | 组件相对少（KRaft 后更少） | 组件更多，要懂 BookKeeper |
| 典型场景 | 日志、流计算、事件总线、大数据管道 | 云上多租户 MQ、队列+流统一、灵活订阅 |

## 存储与扩容怎么讲透？

- Kafka 扩分区/Broker 可能触发 **副本重分配**，大集群耗时长。  
- Pulsar 数据在 Bookie；Broker 故障可在其他 Broker 快速恢复服务。  
- 但 BookKeeper 的磁盘、写延迟、ledger 回收要单独治理。

## 怎么选型？

更适合 **Kafka**：

- 日志 / 事件流、长期回溯、Flink/Spark/大数据栈深度集成  
- 团队已有成熟 Kafka 运维或云产品  
- 分区 + 消费者组模型足够  

更适合 **Pulsar**：

- 强多租户、统一集群多业务  
- 需要 Exclusive / Failover / Shared / Key_Shared  
- 队列语义（竞争消费、重试、DLQ）与流语义并存  
- 希望 Broker 弹性、存储池化  

## 可靠性怎么对比？

都能高可靠，关键是配置 + 业务幂等：

- Kafka：`acks=all` + ISR + 幂等/事务 + 正确提交 Offset  
- Pulsar：写 quorum + Ledger 持久化 + 正确 Ack Cursor  

**都不是开箱的业务 Exactly-Once**；跨 DB 都要幂等或事务方案。

## 兼容与迁移

- Pulsar 可用 **KoP（Kafka-on-Pulsar）** 等让部分 Kafka 客户端接入（视场景）。  
- 迁移重点：**分区键、消费进度模型、监控指标、运维体系**，不只是协议。

## 30 秒收口

“Kafka 是日志型流存储，分区 + 消费者组，生态与大数据集成强；Pulsar 是存储计算分离，订阅一等公民，多租户和队列语义更好。吞吐与流计算优先 Kafka；云上弹性、多订阅形态和租户治理可评估 Pulsar。无论哪个，生产都抓：副本/法定人数、生产确认、消费进度、积压和业务幂等。”
