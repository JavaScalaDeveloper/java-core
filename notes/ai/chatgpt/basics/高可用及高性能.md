# 高可用与高性能面试笔记

**高性能**：更快、更省资源。 **高可用**：故障时仍可用、可恢复。常一起考：CAP、限流熔断、各组件 HA、水平扩展算法。

---

# 一、理论基础

## CAP

分布式系统三者最多同时满足两个（网络分区 P 现实中必有）：

| | 含义 |
|--|------|
| C 一致性 | 所有节点同一时刻看到相同数据 |
| A 可用性 | 每个请求都能得到响应（不保证最新） |
| P 分区容错 | 网络分区时系统仍能工作 |

**常见取舍：** CP（ZK、Etcd 选主一致性）；AP（Eureka 旧版注册）；**多数业务在分区时保 A，靠最终一致**。

## BASE

基本可用、软状态、**最终一致**——互联网大规模系统的务实选择。

## 高性能 vs 高可用

| | 高性能 | 高可用 |
|--|--------|--------|
| 目标 | 低延迟、高吞吐 | 少宕机、快恢复 |
| 手段 | 缓存、异步、并行、CDN | 冗余、故障转移、限流降级 |
| 矛盾 | 缓存一致性与可用 | 强一致与可用（CAP） |

# 二、高性能通用手段

| 手段 | 说明 |
|------|------|
| **缓存** | 多级缓存、本地+Redis；注意穿透/击穿/雪崩 |
| **异步** | MQ 削峰、CompletableFuture、虚拟线程（IO） |
| **并行** | 多线程、分片、Spark 分区 |
| **池化** | 连接池、线程池 |
| **批处理** | 批量写 DB、Bulk API |
| **压缩** | 传输 Snappy/Gzip、列存 |
| **CDN** | 静态资源边缘 |
| **读写分离** | 主写从读 |
| **无状态** | 水平扩、负载均衡 |

## 负载均衡算法

| 算法 | 特点 |
|------|------|
| 轮询 / 加权轮询 | 简单均匀 |
| 随机 / 加权随机 | |
| **最少连接** | 动态负载 |
| **一致性哈希** | 同 key 同节点；扩缩容迁部分 |
| IP Hash | 会话粘滞 |

## 限流 / 降级 / 熔断

| | 作用 |
|--|------|
| **限流** | 控制速率，防打垮（令牌桶、漏桶、Sentinel） |
| **降级** | 关非核心功能，保核心 |
| **熔断** | 下游故障时快速失败，防雪崩（Hystrix/Sentinel） |

```text
用户 → 网关限流 → 服务熔断 → 降级返回兜底
```

## CPU 过高常见原因（Java）

- 死循环 / 复杂计算  
- 频繁 GC  
- 锁竞争、线程过多  
- 正则回溯、序列化热点  
- 用 Arthas `thread -n`、profiler 定位

# 三、水平扩展算法（纠正常见误区）

| 系统 | 分片单位 | 算法要点 |
|------|----------|----------|
| **MySQL 分库分表** | 表/库 | **业务 shard key** 哈希/范围；非内置算法 |
| **Redis Cluster** | 16384 **slot** | CRC16(key)%16384 |
| **Kafka** | Partition | hash(key)%N |
| **ES** | Primary Shard | routing 哈希 % 主分片数（**创建时固定**） |
| **HBase** | Region | **RowKey 范围**；过大 Split |
| **HDFS** | Block | **NameNode 分配** + 机架感知；非经典一致性哈希环 |

**一致性哈希：** 节点映射环上，增删节点只迁相邻区间；Redis 用 **固定 slot** 更常见。

# 四、各组件高可用（速查）

## MySQL

| 方案 | 要点 |
|------|------|
| 主从复制 | 异步/半同步；读写分离；切换丢数风险 |
| MGR | 组复制，多数派 |
| Orchestrator / MHA | 自动 failover |
| 分库分表 | 写扩展；中间件 ShardingSphere |

## Redis

主从 + **哨兵** 或 **Cluster**（slot 迁移）；见 `DB-Redis.md`。

## Kafka

多 Broker；分区多副本；ISR；Controller；`acks=all`。

## RocketMQ

多 NameServer；Broker **主从/DLedger**；多 Consumer；死信队列 DLQ。

## ES

多节点；**主分片+副本**；专用 Master；分片 rebalance。

## HBase

ZK 选举；**多 Master**；多 RegionServer；HDFS 副本；WAL。

## Hadoop

**NN HA**（QJM+ZKFC）；多 DN；YARN RM HA。

## Flink

JobManager HA（ZK/K8s）；Checkpoint + Savepoint；多 TaskManager。

## 通用模式

```text
冗余 + 自动故障转移 + 健康检查 + 无状态扩缩 + 数据多副本
```

# 六、场景题

## RocketMQ 死信队列满了？

1. 查 **消费失败根因**（毒消息）。  
2. 加 Consumer / 优化消费逻辑。  
3. 调 DLQ 容量（治标）。  
4. 人工处理或跳过毒消息。  
5. 监控 `%RETRY%`、DLQ 堆积告警。

## 10 万任务均匀分到 n 台机器（可扩缩）

| 算法 | 适用 |
|------|------|
| 取模 `taskId % n` | n 固定时简单；**n 变要 rehash** |
| 一致性哈希 + 虚拟节点 | 扩缩容迁部分任务 |
| 队列中心 | 机器作 Consumer 拉任务（**最常用**） |
| 调度中心 | DolphinScheduler/Airflow 分配 |

**生产推荐：** 任务进 **MQ/队列**，Worker 竞争消费 + 幂等；扩机器加 Consumer。

## 任务调度均匀性

- 动态 worker：用 **中心队列** 而非硬编码分片。  
- 长任务：心跳 + 重新分配。  
- 避免单机轮询分配状态不一致。

## 面试速记

| 主题 | 一句话 |
|------|--------|
| CAP | 分区下 C/A 取舍；互联网多最终一致 |
| 三板斧 | 限流、降级、熔断 |
| HA 公式 | 冗余 + 转移 + 无状态 |
| 水平扩展 | 各系统分片单位不同，别全说成一致性哈希 |
| 死信满 | 治根因 + 扩容消费 + 监控 |
| 任务均匀 | 队列 + 多 Worker 竞争 |

**收口：** 高性能靠缓存异步并行；高可用靠冗余和故障转移；分布式先想清楚 CAP 和数据分片谁管。
