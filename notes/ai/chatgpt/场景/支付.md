# 场景面试：支付

> 资金链路：**创建支付单 → 调渠道 → 异步回调 → 更新订单/确认库存**。  
> 考察：状态机、幂等、分布式事务边界、对账、安全、高并发、缓存、读写分离。

---

## 1. 场景与核心挑战

| 挑战 | 说明 |
|------|------|
| **资金安全** | 不能多扣、不能少记、不能重复入账 |
| **幂等** | 渠道回调可能重复；客户端重复提交 |
| **一致性** | 支付成功 ↔ 订单已支付 ↔ 库存确认 ↔ 券核销 |
| **异步** | 支付结果靠回调/查单，不能同步死等 |
| **对账** | 渠道账与内部账必须能核对 |
| **安全** | 签名、防篡改、敏感数据加密 |
| **高并发** | 大促支付尖峰；渠道也有 QPS 限制 |

---

## 2. 业务流程

```text
1. 用户发起支付（orderId, payChannel, amount）
2. 支付服务：
   a. 校验订单：待支付、金额一致、未过期
   b. 幂等：查是否已有进行中的 payment（payment_no / idempotent_key）
   c. 创建 payment 记录：状态 INIT → PAYING
   d. 调微信/支付宝统一下单，拿 prepay_id / 支付链接
   e. 返回客户端调起 SDK
3. 用户渠道侧完成付款
4. 渠道异步回调 notify_url
5. 支付服务：
   a. 验签
   b. 幂等更新 payment SUCCESS（仅当原状态 PAYING）
   c. 发 MQ payment_success 或 直接 RPC 订单服务
6. 订单服务：订单 → 已支付；调库存 confirm；发履约 MQ
7. 定时查单：回调丢失时主动 query 渠道
8. T+1 对账：渠道账单 vs payment 表
```

---

## 3. 架构与数据模型

```text
                    ┌─────────────┐
  客户端 ──────────►│  支付服务    │
                    │ payment 表  │
                    └──────┬──────┘
                           │ 统一下单 / 查单
                    ┌──────▼──────┐
                    │ 微信/支付宝  │
                    └──────┬──────┘
                           │ 回调 notify
                    ┌──────▼──────┐
                    │ 验签+幂等   │
                    └──────┬──────┘
                           │ MQ / RPC
                    ┌──────▼──────┐
                    │ 订单/库存   │
                    └─────────────┘
```

| 表/对象 | 关键字段 |
|---------|----------|
| **payment** | payment_no, order_id, amount, channel, status, channel_trade_no, idempotent_key |
| **payment_notify_log** | 原始回调报文、处理结果（审计） |
| **order** | pay_amount, status, pay_time |

**支付单与订单**：1 订单可多次支付尝试（失败重试），成功仅一条；或 1:1 支付单复用幂等。

---

## 4. 事务与分布式事务

### 4.1 原则

- **支付服务内**：创建 payment + 写 notify 日志 → **本地事务**。  
- **支付成功 → 订单更新**：跨服务，**不用 2PC**；用 **可靠消息 + 幂等** 或 **TCC**（金融强要求时）。

### 4.2 推荐：最终一致 + 幂等

```text
回调处理（支付服务本地事务）：
  BEGIN;
    UPDATE payment SET status=SUCCESS WHERE payment_no=? AND status=PAYING;
    INSERT INTO outbox(event=payment_success, ...);
  COMMIT;
  → MQ 投递

订单服务消费：
  幂等键 payment_no / order_id
  UPDATE order SET status=PAID WHERE order_id=? AND status=WAIT_PAY;
  → 调库存 confirm（RPC，失败重试）
```

### 4.3 TCC（银行/强一致场景）

| 阶段 | 支付 | 订单 | 账户 |
|------|------|------|------|
| Try | 冻结渠道额度/预授权 | 锁单 | 冻结余额 |
| Confirm | 扣款成功落账 | 已支付 | 扣减 |
| Cancel | 释放预授权 | 解锁 | 解冻 |

开发成本高；互联网支付多数 **渠道已保证扣款原子性**，内部用 **状态机+对账** 即可。

### 4.4 与库存

- 下单：**预占**  
- 支付成功：**confirm 扣减**（库存服务幂等 `order_id`）  
- 关单/退款：**release / 回滚库存**

库存 confirm 失败不能回滚用户已付渠道款 → **重试 + 告警 + 人工**；所以 confirm 要极高可用。

---

## 5. 状态机（必画）

```text
payment: INIT → PAYING → SUCCESS
                    ↓      ↓
                 CLOSED  REFUNDING → REFUNDED
                    ↑
              超时关单 / 用户取消
```

```text
order: WAIT_PAY → PAID → ...
         ↓
      CANCELLED（仅未支付）
```

**推进规则**：`UPDATE payment SET status='SUCCESS' WHERE payment_no=? AND status='PAYING'`  
返回 0 行 → 已处理过，**仍返回渠道 success**（幂等）。

---

## 6. 回调幂等（核心）

```text
1. 验签失败 → 返回 fail，让渠道重试（或记录攻击）
2. 验签成功 → 查 payment 状态
3. 已是 SUCCESS → 直接返回 success（渠道停止重试）
4. PAYING → 更新 SUCCESS + 发 MQ（同一事务）
5. 金额不一致 → 告警，不推进状态
6. 记录 notify_log 全量报文
```

**分布式锁**：`payment_no` 维度 Redis 锁，防止并发回调双写（DB 乐观锁通常够）。

---

## 7. 缓存

| 用途 | 策略 |
|------|------|
| 支付中状态 | Redis `pay:order:{orderId}` 短 TTL，防重复发起 |
| 渠道路由 | 本地缓存渠道配置 |
| 限流 | Redis 用户/商户维度计数 |
| 订单金额校验 | **以 DB 为准**，不依赖缓存金额 |

**不缓存**支付最终结果作唯一真相；以 **payment 表 + 主库** 为准。

---

## 8. 读写分离

| 操作 | 路由 |
|------|------|
| 创建支付、回调更新 | **主库** |
| 支付流水查询、对账导出 | **从库** / 离线库 |
| 用户支付结果页 | **读主** 或 查单后读主 |

对账任务：读从库或只读实例，避免影响在线。

---

## 9. 高并发

| 手段 | 说明 |
|------|------|
| **限流** | 支付接口、回调接口、按商户 QPS |
| **异步** | 回调只更新 payment + 发 MQ；订单/库存异步 |
| **连接池** | 与渠道 HTTP 客户端独立池、超时合理 |
| **削峰** | 回调 MQ 消费可扩消费者 |
| **降级** | 某渠道故障切备用渠道（配置中心） |
| **隔离** | 回调线程池与下单隔离 |

渠道侧也有峰值限制；需 **排队 + 友好提示**。

---

## 10. 安全

| 项 | 做法 |
|----|------|
| **验签** | 渠道公钥验证 notify 签名 |
| **HTTPS** | 回调 URL 必须 HTTPS |
| **金额** | 服务端按 order 算 amount，不信客户端 |
| **防重放** | 幂等 + 状态机 |
| **敏感信息** | 卡号/token 不落日志；PCI 合规 |
| **IP 白名单** | 部分渠道支持回调 IP 校验 |

---

## 11. 查单与超时

| 机制 | 说明 |
|------|------|
| **主动查单** | 回调 N 分钟未到 → 定时任务 query 渠道 |
| **支付超时** | order WAIT_PAY 超时关单；payment PAYING 超时 CLOSED |
| **长轮询/WebSocket** | 前端支付结果页，减少盲刷 |

**回调 vs 查单** 谁先谁后：都要幂等；以 **先成功更新 payment 的为准**。

---

## 12. 退款（联动）

见 [退款.md](./退款.md)。要点：

- 退款单独立状态机；部分退、多次退  
- 渠道退款异步；**退款回调也要幂等**  
- 订单 PAID → REFUNDING → REFUNDED  
- 库存回滚、券退回按产品规则

## 13. 对账

```text
每日 T+1：下载渠道对账单
  与 payment 表 channel_trade_no、amount、status 核对
  长款/短款/状态不一致 → 差错表 → 人工/自动补单
```

**清结算**见 [对账清结算.md](./对账清结算.md)。

---

## 14. 面试追问

| 追问 | 要点 |
|------|------|
| 回调重复怎么办？ | 状态机 + 幂等；已 SUCCESS 直接 OK |
| 回调成功但 MQ 丢了？ | Outbox 重试；订单未 PAID 则查单/补偿任务 |
| 用户付了订单未更新？ | 查单 + 补偿；对账兜底 |
| 双写支付和订单用 Seata？ | 一般不用；MQ+幂等；金融可 TCC |
| 如何防篡改金额？ | 服务端 order 金额；回调比对 |

---

## 15. 30 秒收口

「支付单独 **payment 状态机**；统一下单后等 **渠道回调验签+幂等** 更新 SUCCESS，**Outbox/MQ** 驱动订单 PAID 和库存 confirm。跨服务 **最终一致+幂等**，资金以 **payment 表+对账** 兜底。回调、查单、MQ 消费全链路幂等；读写：写主读从，结果页读主。」
