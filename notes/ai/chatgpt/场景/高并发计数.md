# 场景面试：高并发计数（点赞 / 浏览量 / 热搜）

> 典型：文章点赞、视频播放量、微博热搜热度、商品浏览 PV/UV。  
> 核心矛盾：**写极多、读也大、热点 Key 集中**，业务通常允许 **秒～分钟级误差**，不以强一致事务扛写。

---

## 1. 业务拆解

| 场景 | 计数语义 | 精度要求 | 去重 |
|------|----------|----------|------|
| **点赞** | 每人对目标最多 +1 | 较准（可对账） | 必须（user 维度） |
| **浏览 PV** | 每次打开 +1 | 可近似 | 不去重 |
| **浏览 UV** | 独立访客 | 可近似（1% 误差可接受） | HyperLogLog / BitMap |
| **热搜热度** | 加权分（搜索+互动+时间衰减） | 榜单相对序准即可 | 见 [排行榜.md](./排行榜.md) |

**面试第一句**：「计数用 **Redis INCR / HLL 抗写**，异步批量刷 DB；热点 **分片+本地聚合**；展示读 Redis，接受最终一致。」

---

## 2. 整体架构

```text
客户端 点赞/浏览
    │
    ▼
网关限流（防刷）
    │
    ▼
计数服务
    ├─① Redis：INCR / HINCRBY / PFADD（UV）/ SADD+INCR（去重点赞）
    ├─② 可选：本地缓冲（per-pod 聚合）→ 定时/阈值刷 Redis
    └─③ 异步：MQ / 定时任务 批量 flush → MySQL
    │
读路径：Redis 优先 → miss 读 DB 回填 → 返回
```

| 层 | 职责 |
|----|------|
| **Redis** | 实时计数真相（在线路径） |
| **MQ / 批量任务** | 削峰、异步落库 |
| **MySQL** | 持久化、对账、报表、冷启动回填 |
| **本地缓存** | 热点 count 短 TTL 展示（可选二级） |

---

## 3. 写路径细节

### 3.1 PV / 简单计数

```text
INCR count:pv:article:{id}
（可选）RPUSH / XADD 变更流水 → 消费者聚合写 DB
```

### 3.2 UV（HyperLogLog）

```text
PFADD uv:article:{id}  userId|deviceId
PFCOUNT uv:article:{id}   → 近似 UV
```

| 方案 | 精度 | 内存 | 适用 |
|------|------|------|------|
| **HLL** | ~0.81% 标准误 | 极省（~12KB/key） | 大盘 UV |
| **BitMap** | 精确（需映射 uid→offset） | 随用户规模涨 | 日活、活动 UV |
| **Set** | 精确 | 大 | 仅小集合 |

### 3.3 去重点赞（必考）

```text
Lua 原子：
  if SADD like:users:{targetId} userId == 1 then
      INCR like:count:{targetId}
      return 1
  else return 0
```

- DB 兜底：唯一索引 `(user_id, target_id)`，异步落库冲突则忽略  
- 取消赞：`SREM` + `DECR`（注意 DECR 不低于 0）

---

## 4. 热点 Key 治理

| 手段 | 说明 |
|------|------|
| **Key 分片** | `like:{id}:{hash(userId)%N}`，读时 SUM N 片 |
| **本地聚合** | 进程内 `ConcurrentHashMap` 累加，100ms/1k 次刷 Redis |
| **读写分离展示** | 展示用本地 Caffeine 缓存 count，后台异步刷新 |
| **Cluster** | 避免单 slot 打爆；分片后 hash tag 需谨慎设计 |
| **隔离** | 爆款单独 Redis DB/实例（可选） |

```text
写：INCR like:{aid}:{shard}
读：SUM(INCR like:{aid}:0..N-1) 或 维护一份汇总 key 异步合并
```

---

## 5. 异步落库与一致性

```text
策略 A：定时扫 Redis Key → UPSERT DB（适合 PV）
策略 B：每次变更发 MQ → 消费者批量（buffer 1s / 500 条）写 DB
策略 C：只存增量流水表，离线汇总（适合分析）
```

| 问题 | 处理 |
|------|------|
| Redis 与 DB 差多少？ | **最终一致**；定时对账以 Redis 为准或「大数取 Redis、纠偏用 DB」 |
| Redis 宕机丢计数？ | AOF/RDB；关键计数可再以 DB 唯一表重算 |
| 重复 flush？ | UPSERT / `count = GREATEST` / 幂等任务 id |
| 展示要「准」？ | 个人页/运营后台读 DB；C 端读 Redis |

**事务**：无跨库强事务；点赞「关系」可强（唯一约束），「计数」弱一致。

---

## 6. 读写分离

| 操作 | 走哪 |
|------|------|
| 实时展示 count | Redis |
| 异步落库写 | MySQL **主库** 批量 |
| 报表 / BI | 从库或数仓 |
| Redis miss 回填 | 优先主库短路径，或接受从库延迟 |

---

## 7. 缓存问题（本场景特有）

| 问题 | 对策 |
|------|------|
| **击穿** | 热点 count **永不过期** 或逻辑过期 + 异步刷；回填加锁 |
| **雪崩** | flush 任务错峰；TTL 加随机（若用过期策略） |
| **穿透** | 非法 id 布隆 / 空值短缓存，避免对不存在文章疯狂 INCR |
| **Big Key** | 点赞用户 Set 过大 → 分片 Set 或仅存「已赞」Bloom+DB |

---

## 8. 幂等与防刷

- 点赞：`SADD` / DB 唯一 → 天然幂等  
- 浏览：允许重复计；防刷靠网关 IP/设备频控（见 [限流防刷.md](./限流防刷.md)）  
- 热搜加分：同一用户同一词滑动窗口限频，防刷榜

---

## 9. 异常与降级

| 异常 | 处理 |
|------|------|
| Redis 超时 | 降级：跳过计数 / 只记本地 MQ 稍后补；展示返回旧值或「-」 |
| MQ 堆积 | 扩大批量、合并同 key；丢弃过期浏览流水（产品允许） |
| 计数为负 | DECR 前校验；对账修正 |
| 分片汇总慢 | 异步维护 `like:sum:{id}` |

---

## 10. 面试追问

| 追问 | 答点 |
|------|------|
| 为什么不每次写 DB？ | 写放大、行锁；Redis 内存操作 + 批量落库 |
| HLL 能取消 UV 吗？ | **不能**精确删除；取消赞不要用 HLL |
| 和排行榜区别？ | 计数是标量 INCR；榜是 ZSet 排序，见排行榜专题 |
| 如何保证点赞不丢？ | 先写 Redis 关系+计数，MQ 落库；失败重试；以 DB 唯一对账 |
| 百万赞 Set 内存？ | 分片 / 只缓存近期活跃 / 冷数据只留 count+DB |

---

## 11. 30 秒收口

「点赞浏览用 **Redis 抗写**（INCR/HLL/SADD+Lua），**异步批量刷 DB** 最终一致；热点 **分片+本地聚合**；读走 Redis，穿透击穿按常规缓存手段；接受短暂不准，对账纠偏。」
