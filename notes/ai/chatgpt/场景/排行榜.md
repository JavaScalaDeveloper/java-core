# 场景面试：排行榜（百万级 + 实时）

> 典型：游戏积分榜、直播打赏榜、活动 PK、热搜榜、销量榜。  
> 核心：**高并发写分** + **实时 TopN / 我的排名** + **百万用户量级**。

---

## 1. 需求拆解

| 需求 | 说明 | 难点 |
|------|------|------|
| **更新分数** | 行为触发加分/减分 | 写 QPS 高 |
| **Top N** | 前 10/100/1000 | 读频繁、要快 |
| **我的排名** | 用户查「我排第几」 | 百万级要 O(logN) |
| **附近排名** | 我前后各 5 名 | ZREVRANK + 范围查 |
| **实时性** | 秒级甚至亚秒级可见 | 与 DB 异步落库的平衡 |
| **量级** | 百万～千万参与者 | 内存、热点 Key、Cluster |
| **周期榜** | 日榜/周榜/赛季榜 | 过期、归档、重置 |

**面试第一句**：「百万级实时榜 **Redis Sorted Set** 为主；写走内存、**异步落库**；超热榜 **分片/分桶**；周期榜 **按时间切 Key**。」

---

## 2. 为什么选 Redis ZSet？

| 方案 | 百万级 TopN | 我的排名 | 实时写 | 评价 |
|------|-------------|----------|--------|------|
| **MySQL ORDER BY** | 慢（全表排序/大 offset） | 子查询慢 | 行锁竞争 | 仅离线榜 |
| **ES** | 可以 | 可以 | 近实时 | 重、成本高 |
| **Redis ZSet** | **O(logN+M)** | **O(logN)** | **O(logN)** | **在线榜首选** |
| **内存 + 定时快照** | 可以 | 可以 | 快 | 自研等价 ZSet |

ZSet 底层：**跳表 + 哈希**，按 **score 排序**，member 唯一。

```text
ZADD board:20250827  score  member(userId)
ZINCRBY board:20250827  delta  userId
ZREVRANGE board:20250827  0 99 WITHSCORES     → Top100
ZREVRANK board:20250827  userId                 → 我的排名（0-based）
ZSCORE board:20250827  userId                   → 我的分数
```

## 3. 整体架构

```text
                    ┌──────────────┐
  行为（游戏/打赏）──►│  榜单服务     │
                    └──────┬───────┘
                           │
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    Redis ZSet（实时）   MQ（削峰）    MySQL（持久/审计）
           │               │               │
           │               └──────────────►│ 异步批量 upsert
           ▼                               ▼
    TopN 缓存 / 本地缓存              离线榜 / 对账 / 赛季归档
```

| 层 | 职责 |
|----|------|
| **Redis** | 实时分数、排名、TopN |
| **MQ** | 写峰值削峰；异步落库 |
| **MySQL** | 持久化、历史赛季、报表（非实时读主路径） |
| **CDN/本地缓存** | TopN 结果短缓存（可选） |

## 4. 分数（score）设计

### 4.1 整数分

```text
ZINCRBY board:gift:live123  100  userId:10086
```

简单；注意 **整数溢出**（Redis score 是 double，极大值仍够用）。

### 4.2 同分排序（tie-break）—— 必考

ZSet **同 score 按 member 字典序** 排，**不能**表达「同分先达到者靠前」。

**做法：把「真实排序依据」编码进 score（52 位常见）**

```text
score = 业务分 * 1e13 + (MAX_TS - event_ts)
        └─ 高位：分高者优先
        └─ 低位：同分则时间早（ts 小）者优先
```

或使用 **复合 member**：`member = f"{score:010d}:{ts:013d}:{userId}"`（读 TopN 时解析，查个人排名仍用 userId 作 member 更简单）。

**推荐（工程常见）**：

```text
displayScore = 业务分（整数）
redisScore   = displayScore + (1 - ts/1e13)   // 同分越小越靠前，需验证精度
```

面试说清：**「同分要用 score 低位带时间戳，或拆成两个 ZSet 二次排序。」**

### 4.3 先达优先 vs 后达优先

- 活动榜通常 **先达同分者名次高** → `MAX_TS - ts` 放低位。  
- 游戏某些榜 **相同分并列同名次** → 产品层展示「并列第 5」，ZSet 仍字典序，可接受。

## 5. 写路径（高并发更新）

### 5.1 同步写 Redis（主路径）

```text
1. 业务校验（活动有效、防刷）
2. ZINCRBY / ZADD（Lua 保证上限、防减到负）
3. 返回最新 score（可选 ZSCORE）
4. 异步：发 MQ score_changed { boardId, userId, delta, ts }
```

**Lua 示例逻辑**：

```lua
-- 加分且不超过上限
local s = redis.call('ZINCRBY', KEYS[1], ARGV[1], ARGV[2])
if tonumber(s) > tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[3], ARGV[2])
  return ARGV[3]
end
return s
```

### 5.2 异步落库

```text
MQ 消费 → 批量 INSERT ... ON DUPLICATE KEY UPDATE score=...
```

- 实时榜 **以 Redis 为准**；DB **最终一致**。  
- 重启恢复：DB 全量/增量 **灌回 Redis**（低峰）。

### 5.3 写削峰

| 手段 | 说明 |
|------|------|
| **MQ 合并** | 100ms 内同一 user 多次加分合并 |
| **本地聚合** | 接入层内存累加再 flush Redis |
| **限流** | 单用户/单 IP 加分频率 |

## 6. 读路径

### 6.1 Top N（最热点读）

```text
ZREVRANGE board:xxx 0 99 WITHSCORES
```

**优化**：

- Top100 **结果缓存 1～3 秒**（本地 Caffeine + Redis）；写频繁时 **订阅/版本号** 失效。  
- 展示层批量 **mget 用户信息**（昵称、头像）。

### 6.2 我的排名 + 我的分数

```text
ZSCORE board:xxx userId
ZREVRANK board:xxx userId    → rank + 1 展示（注意并列产品规则）
```

复杂度 **O(logN)**，百万级可接受（单次 ~20 次指针跳转量级）。

### 6.3 我附近排名

```text
rank = ZREVRANK key userId
ZREVRANGE key rank-5 rank+5
```

### 6.4 分页榜（101～200 名）

```text
ZREVRANGE key 100 199 WITHSCORES
```

深分页在 ZSet 里 **比 MySQL offset 友好**；仍建议 **限制最大可见名次**（如只展示前 1 万）。

## 7. 百万级规模问题与方案

### 7.1 内存估算

```text
每个 member ≈ userId(8B) + score(8B) + 跳表指针开销 ≈ 几十～上百字节
100 万用户 ≈ 100MB～300MB 量级（单榜）
```

Redis Cluster **单 Key 单 slot**；一个 ZSet 100 万元素 **可放在一个 Key**（常见做法）。

### 7.2 热点 Key（单榜全网一个 Key）

| 风险 | 方案 |
|------|------|
| 单 slot 过热 | Redis Cluster 仍 **单 Key 单节点**；靠 **主从读**、**本地缓存 TopN** |
| 写热点 | 写合并、MQ 削峰 |
| 读热点 | TopN 本地缓存；**读写分离**（Replica 读 ZREVRANGE，写 Master） |

**注意**：Redis Cluster 下 **ZREVRANK 必须走主** 或容忍副本延迟；TopN 可走从。

### 7.3 超大榜（千万级 / 单 Key 过大）

| 方案 | 说明 |
|------|------|
| **只保留 Top M** | 定期 ZREMRANGEBYRANK 删掉榜外；榜外用户显示「1 万+」 |
| **分桶** | `board:shard:{hash(userId)%K}` 分 K 个 ZSet，TopN **归并**（类似 MapReduce） |
| **多级榜** | 省榜/市榜/全国榜分开 Key |
| **近似排名** | 榜外用户不保证精确 rank，仅展示 score 区间 |

**分桶 TopN 归并**：

```text
各 shard 取 Top 200 → 200*K 条小顶堆归并 → 最终 Top 100
适用于「超大规模 + 只需精确 Top 几百」
```

### 7.4 多榜并存

```text
board:daily:20250827
board:weekly:2025W35
board:live:{roomId}
board:gift:{anchorId}:daily
```

按 **活动/房间/时间** 切 Key，避免一个 ZSet 无限膨胀。

## 8. 周期榜（日榜/周榜/赛季）

### 8.1 Key 按时间滚动

```text
board:activity42:20250827     TTL 48h
board:activity42:20250828
```

零点 **新 Key**；旧 Key 设 TTL 延迟删除或 **归档到 MySQL**。

### 8.2 重置

- 新周期 **新 ZSet**，不清空旧 Key（防误操作）。  
- 赛季结束：Redis 快照 **持久化** + 发奖励 MQ（幂等 `season_id+userId`）。

### 8.3 定时任务

- XXL-Job 扫 **待归档榜** → 写 DB → 删 Redis（低峰）。

## 9. 实时性 vs 准确性

| 级别 | 做法 | 延迟 |
|------|------|------|
| **强实时** | 行为后直接 ZINCRBY | 毫秒级 |
| **准实时** | MQ 合并 100ms 批量 ZINCRBY | 百毫秒 |
| **展示缓存 TopN** | 1s 本地缓存 | 用户感知 1s |
| **DB 持久** | 异步 秒～分钟 | 不影响榜面 |

**活动结束瞬间**：停止写 → **最后一轮 ZREVRANGE 定榜** → 发奖；加 **分布式锁** 防并发定榜。

---

## 10. 事务 / 一致性

| 场景 | 方案 |
|------|------|
| 加分 + 扣库存（打赏） | **本地事务** 扣币 + MQ；**Redis 加分** 异步或同一 Lua 前先校验余额 RPC |
| 加分 + 发奖 | **定榜后** MQ 发奖，幂等 |
| Redis 与 DB | **以 Redis 为在线真相**；DB 异步；故障 **DB 回放** |

不用 Seata 绑「Redis + MySQL」强事务。

---

## 11. 防刷与风控

- 单用户 **加分上限/冷却**  
- 设备/IP **限流**（见 [限流防刷.md](./限流防刷.md)）  
- 异常分数 **人工审核** + ZREM  
- 积分来源 **流水表** 可对账 Redis

---

## 12. 与 MySQL 的配合

| MySQL 用途 | 说明 |
|------------|------|
| **流水** | `score_log(user_id, delta, reason, ts)` |
| **快照** | 每小时/定榜 `board_snapshot(rank, user_id, score)` |
| **离线榜** | T+1 报表、复杂维度（地区） |
| **恢复** | Redis 故障从 snapshot + log 重建 |

**复杂排序**（多维度过滤）：离线 **ClickHouse/ES**；在线仍 Redis TopN + 简单规则。

---

## 13. 读写分离

- **写**：Redis Master `ZINCRBY`  
- **读 TopN**：可 Replica `ZREVRANGE`（ tolerate 短暂旧数据）  
- **读我的排名**：建议 **Master** 或 接受副本延迟  
- MySQL：流水写主；报表读从

---

## 14. 缓存层次

```text
L1 本地：Top100 1s
L2 Redis：ZSet 全量
L3 MySQL：归档
```

写后：**递增 board_version**；读 TopN 带 version 失效本地缓存。

## 15. 面试追问

| 追问 | 要点 |
|------|------|
| 为什么不用 MySQL？ | 百万行 ORDER BY + 高并发 UPDATE 扛不住；排名要 O(logN) |
| 同分怎么办？ | score 低位嵌时间戳；或并列名次产品规则 |
| Redis 挂了？ | 降级只展示 DB 昨日榜；或只读模式；恢复后灌数 |
| 1000 万人都上榜？ | 截断榜外 + 分桶归并 TopN；榜外不保证精确 rank |
| 如何定榜发奖？ | 停写 + 锁 + ZREVRANGE + 幂等发奖 MQ |
| ZSet 和 List 区别？ | ZSet 按 score 排序；List 只能头尾 |

---

## 16. 方案选型简表

| 规模 | 写 QPS | 推荐 |
|------|--------|------|
| < 10 万 | 低 | 单 ZSet + 异步 DB |
| 100 万 | 高 | ZSet + TopN 缓存 + MQ 落库 |
| 1000 万+ | 极高 | 分桶 / 截断榜外 / 多级榜 |
| 复杂分析 | — | 在线 Redis + 离线 OLAP |

---

## 17. 30 秒收口

「百万级实时榜用 **Redis ZSet**：`ZINCRBY` 写、`ZREVRANGE` 取 TopN、`ZREVRANK` 查名次；**同分 score 低位带时间戳**；写 **异步落 MySQL** 做持久与对账；周期榜 **按日切 Key+TTL**；超大规模 **Top 截断或分桶归并**；TopN **短缓存** 抗读热点。」
